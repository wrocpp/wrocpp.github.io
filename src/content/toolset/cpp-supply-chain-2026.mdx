A C++ supply chain in 2026 is a package manager, an SBOM emitted on every build, a vulnerability scanner in CI, build provenance, and a plan for the next OpenSSL advisory. This page maps that stack, says which parts I re-ran on 2026-11-06, and shows a reflection pattern for one gap: the SBOM that drifts from the code.

## In short

- Re-run on 2026-11-06: the reflection SBOM example, on Clang (Bloomberg fork), GCC 16.2 and GCC trunk. Not re-run: syft, grype, vcpkg, Conan, cosign and the CI recipe.
- CMake 4.5 adds `install(SBOM)` and `export(SBOM)`, and the documentation says CMake currently writes SPDX 3.0 JSON-LD. The newest release on cmake.org on 2026-11-06 was 4.5.0-rc3, so check that it has shipped before you rely on it.
- The earlier text gave "SLSA Level 3 / 4". SLSA v1.0 defines Build levels L0 to L3, and the specification is now at v1.2.
- Missing annotations are caught, but the error names the rule, not the member.
- For the EU Cyber Resilience Act, reporting obligations apply from 11 September 2026 and the main obligations from 11 December 2027.

## Today

### The 2026 supply-chain stack

| Layer | Tool | Notes |
|---|---|---|
| Package manager | [vcpkg](https://vcpkg.io/) or [Conan](https://conan.io/) | Pick one and stick to it. Mixing causes pain. |
| SBOM emit | [syft](https://github.com/anchore/syft) (source tree and container), or CMake 4.5 `install(SBOM)` for your own targets | syft writes `cyclonedx-json`, `spdx-json` and others; choose a version with `-o <format>@<version>`. CMake writes SPDX 3.0 JSON-LD. |
| Vulnerability scan | [grype](https://github.com/anchore/grype) | Scans an SBOM (`grype sbom:./sbom.json`); `--fail-on critical` makes it exit non-zero. |
| Build provenance | [in-toto](https://in-toto.io/) attestations and [SLSA](https://slsa.dev/) | SLSA v1.0 Build levels run L0 to L3; there is no Level 4. |
| Signing | [sigstore](https://www.sigstore.dev/) cosign | Sign and verify artefacts; keyless signing uses an OIDC identity. |

### CMake recipe

```cmake
# vcpkg manifest mode: vcpkg.json next to CMakeLists.txt
include($ENV{VCPKG_ROOT}/scripts/buildsystems/vcpkg.cmake)

find_package(nlohmann_json CONFIG REQUIRED)
find_package(fmt          CONFIG REQUIRED)
find_package(OpenSSL      REQUIRED)

target_link_libraries(your_target PRIVATE
    nlohmann_json::nlohmann_json fmt::fmt OpenSSL::SSL OpenSSL::Crypto)
```

### CI recipe

```yaml
# .github/workflows/sbom.yml: emit and scan on every push
- run: syft . -o cyclonedx-json > sbom.cdx.json
- run: grype sbom:sbom.cdx.json --fail-on critical
- uses: actions/upload-artifact@v4   # v7.0.2 was the latest release on 2026-11-06
  with:
    name: sbom
    path: sbom.cdx.json
```

The `--fail-on critical` option is the load-bearing line. Grype's source lists five severities, from negligible up to critical. Without it grype reports and exits 0. I read this in grype's source on 2026-11-06 and did not run the recipe.

### Where conventional SBOM workflows leak

The common pattern is a side-channel manifest (YAML) listing each vendored dependency, version, license and purl. The build pipeline reads it, emits CycloneDX from it and scans with grype. The manifest drifts. A new dep gets vendored without a manifest entry. An old dep gets removed but the manifest entry stays. License changes between versions; the manifest holds the old one. Each drift is a finding waiting for an audit.

The next section closes the gap by encoding component metadata as P3394 annotations on the integration type. If the dep is not in the source, it cannot be in the SBOM. If you remove the integration type, the SBOM entry vanishes on the next build.

## Reflection today

Encode each vendored component as a templated P3394 annotation on the integration type. A consteval walker emits the CycloneDX components fragment AND `static_assert`s every member carries the annotation. The source is the only declaration of the component list, so that list cannot drift from the source. The scanner still needs the built artefact: this check covers declared vendored code only.

```cpp
namespace sbom {
template <fixed_string Name, fixed_string Version,
          fixed_string Purl, fixed_string License>
struct component {
    static constexpr auto name    = Name.view();
    static constexpr auto version = Version.view();
    static constexpr auto purl    = Purl.view();
    static constexpr auto license = License.view();
};
}

struct VendoredComponents {
    [[=sbom::component<
        "nlohmann-json", "3.11.3",
        "pkg:github/nlohmann/json@v3.11.3", "MIT">{}]]
    struct nlohmann_json_tag {} json;

    [[=sbom::component<
        "fmt", "10.2.1",
        "pkg:github/fmtlib/fmt@10.2.1", "MIT">{}]]
    struct fmt_tag {} fmt;

    [[=sbom::component<
        "openssl", "3.2.1",
        "pkg:github/openssl/openssl@openssl-3.2.1", "Apache-2.0">{}]]
    struct openssl_tag {} openssl;
};

emit_components<VendoredComponents>();   // emits CycloneDX 1.5 JSON (the current CycloneDX release is 1.7)
```

Walker output:

```json
{
  "bomFormat": "CycloneDX",
  "specVersion": "1.5",
  "components": [
    { "type": "library", "bom-ref": "nlohmann-json", "name": "nlohmann-json",
      "version": "3.11.3", "purl": "pkg:github/nlohmann/json@v3.11.3",
      "licenses": [{ "license": { "id": "MIT" } }] },
    { "type": "library", "bom-ref": "fmt", "name": "fmt",
      "version": "10.2.1", "purl": "pkg:github/fmtlib/fmt@10.2.1",
      "licenses": [{ "license": { "id": "MIT" } }] },
    { "type": "library", "bom-ref": "openssl", "name": "openssl",
      "version": "3.2.1", "purl": "pkg:github/openssl/openssl@openssl-3.2.1",
      "licenses": [{ "license": { "id": "Apache-2.0" } }] }
  ]
}
```

Add a member without the annotation and the build refuses. On 2026-11-06 I added `struct zlib_tag {} zlib;` with no annotation. Both GCC 16.2 and the Bloomberg Clang fork reported `static assertion failed: supply-chain: every member of the vendored bundle must carry an [[=sbom::component<...>{}]] annotation`, pointing at the walker's `static_assert`, and then a second error from the splice. The message does not name `zlib`. The fragment can be merged with the output of a tool such as syft; I did not run that merge.

### Composable with the safety walkers

The same `nonstatic_data_members_of` walker that drives the SBOM emit also drives the [hardened-stdlib schema lint](/toolset/hardened-stdlib/), the [qualified-compilers MISRA Rule 11.0.1 lint](/toolset/qualified-compilers/), the [lifetime-safety borrow lint](/toolset/lifetime-safety-2026/), and the [SoA layout transform](/toolset/simd-in-cpp-2026/). One walker, five orthogonal rules. The SBOM-component-required rule is just another predicate; add a sixth, the schema enforces it.

## What changed in the news

As of 2026-11-06:

- The EU Cyber Resilience Act's reporting obligations for actively exploited vulnerabilities and severe incidents apply from 11 September 2026. ENISA launched its [single reporting platform](https://www.enisa.europa.eu/news/the-cra-single-reporting-platform-is-launched) that day. The main obligations apply from 11 December 2027, per the [Commission's CRA page](https://digital-strategy.ec.europa.eu/en/policies/cyber-resilience-act). Germany's implementing law passed the Bundestag on 15 October per my research notes; I did not find a primary source to cite, so treat that as unverified. See <PostLink slug="cra-reporting-live-qt-declaration">the CRA post</PostLink> for the Qt side.
- libstdc++ fixed two library bugs in October, CVE-2026-114691 (`vector<bool>` constructors) and CVE-2026-114690 (parallel `std::search`). The fixes are on the gcc-14, gcc-15 and gcc-16 branches and in no point release as of 2026-11-06. A vendored or system copy of libstdc++ is a dependency too: check which headers your build actually uses. The [hardened-stdlib](/toolset/hardened-stdlib/) page has the detail.
- CMake 4.5.0-rc3 is the newest release on cmake.org (4 November). `install(SBOM)` and `export(SBOM)` describe your own installed targets from the build system. They are not a scanner and do not replace syft for the dependencies you consume.

## Where this is heading

These are sketches, not code that any compiler accepts. Token injection ([P3294](https://wg21.link/p3294), latest revision R2 from 2024) is a C++29 candidate that could let a declaration generate wrapper code:

```cpp
// Sketch only. P3294 describes code injection with token sequences;
// this attribute form and vcpkg::dep are illustrations, not paper syntax.
[[ inject(sbom_component) ]]
using nlohmann_json = vcpkg::dep<"nlohmann-json", "3.11.3">;
```

Profiles (P3589R2 framework, not in the C++26 draft) have no `sbom_required` profile in any paper I read. The idea of a translation unit that may include only annotated vendored types is mine:

```cpp
// Sketch only: sbom_required is invented for this page.
[[ profiles::enforce(sbom_required) ]]
namespace prod_app { /* every external symbol through an annotated wrapper */ }
```

The state of play on 2026-11-06 is a toolchain SBOM from a scanner, plus an in-source fragment from the walker, merged at build time. Whether C++29 changes that is open, and the C++26 ballot result does not affect any tool on this page.
