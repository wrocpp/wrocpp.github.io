Many memory-safety bugs in production C++ are plain library misuse: `v[i]` with an index from an untrusted file, `*ptr` on a null smart pointer, `s.front()` on an empty string. Hardening turns those preconditions into checks that stop the program. P3471R4 (Varlamov and Dionne) puts it in the C++26 working draft, and the draft was reported disapproved in the ISO ballot that closed on 22 October according to P4433R0 (<PostLink slug="c26-dis-ballot-result">the ballot post</PostLink>). The settings below are vendor settings that exist whatever happens to the draft.

## In short

- As of 2026-11-06, hardening is in the C++26 draft, not in a ratified standard. libstdc++, libc++ and the MSVC STL ship their own settings, and I ran each on Compiler Explorer.
- A vector read at index 42 of a three-element vector printed `0` and exited 0 with nothing set (libstdc++ at `-O2`, libc++ 23.1.0, MSVC 19.51). The libc++, libstdc++ and MSVC settings I ran each stopped it.
- libc++ `FAST` and `EXTENSIVE` trap without a message (SIGILL). libstdc++ prints an assertion and aborts. The MSVC STL ends the process with `__fastfail`.
- P3471R4 cites Google: a performance impact "as low as 0.3%" and over 1000 bugs. The earlier text said "on average", "no regressions" and "Google's default", none of which the paper says, and I removed them.
- libstdc++ fixes for CVE-2026-114691 (`vector<bool>` sizes near `SIZE_MAX` wrap) and CVE-2026-114690 (parallel `std::search`) are on the gcc-14, 15 and 16 branches since 29 October. As of 2026-11-06 they are in no point release.
- `-fhardened` has to reach the link step, `_GLIBCXX_ASSERTIONS` is already on in unoptimized builds, and the libc++ default is none. The CMake line below reflects that.

## Today

### One setting per implementation

```cmake
if(CMAKE_CXX_COMPILER_ID MATCHES "Clang")
    # Applies when building against libc++. With libstdc++ use the GNU macro.
    add_compile_definitions(
        _LIBCPP_HARDENING_MODE=_LIBCPP_HARDENING_MODE_FAST
    )
elseif(CMAKE_CXX_COMPILER_ID STREQUAL "GNU" AND CMAKE_SYSTEM_NAME STREQUAL "Linux")
    add_compile_options(-fhardened)   # GCC 14+, GNU/Linux only
    add_link_options(-fhardened)      # the umbrella adds -pie and -Wl,-z,relro,-z,now
elseif(CMAKE_CXX_COMPILER_ID STREQUAL "MSVC")
    add_compile_definitions(_MSVC_STL_HARDENING=1)   # VS 2022 17.14 and later
endif()
```

I did not run this fragment through CMake (not re-run on 2026-11-06). I ran each flag by hand on Compiler Explorer, below. Put it near the top of the top-level `CMakeLists.txt`, before the targets are created. Subdirectories added afterwards pick it up.

### What each setting did

The test program reads one element past the end of a vector:

```cpp
#include <vector>
#include <print>
int main(){ std::vector<int> v={1,2,3}; std::println("{}", v[42]); }
```

| Implementation and setting | Catches | Result on Compiler Explorer, 2026-11-06 |
|---|---|---|
| libc++ 23.1.0, nothing set | nothing | printed `0`, exit 0 |
| libc++ `_LIBCPP_HARDENING_MODE_FAST` | bounds checks on element access and input ranges. The libc++ docs recommend it for production | no output, SIGILL (exit 132) |
| libc++ `_LIBCPP_HARDENING_MODE_EXTENSIVE` | FAST plus null-pointer checks and further cheap checks | no output, SIGILL (exit 132) |
| libc++ `_LIBCPP_HARDENING_MODE_DEBUG` | every available check, with message text. Not for production, per the docs | `vector.h:414: libc++ Hardening assertion __n < size() failed: vector[] index out of bounds`, SIGABRT |
| libstdc++ (GCC 16.2) at `-O2`, nothing set | nothing | printed `0`, exit 0 |
| libstdc++ `-D_GLIBCXX_ASSERTIONS` at `-O2` | precondition checks, such as string and vector bounds | `stl_vector.h:1253: ... Assertion '__n < this->size()' failed.`, SIGABRT |
| libstdc++ at `-O0`, nothing set | the same checks, which are on by default in unoptimized builds | the same assertion, SIGABRT |
| libstdc++ `-fhardened` at `-O2` | defines `_GLIBCXX_ASSERTIONS` and `_FORTIFY_SOURCE=3`, among other flags | both macros defined (checked with `#ifdef`) |
| libstdc++ `-D_GLIBCXX_DEBUG` | adds iterator checks. It changes container sizes, so debug and non-debug code cannot exchange container instances (libstdc++ manual) | not run |
| MSVC STL, `/D_MSVC_STL_HARDENING=1` | `vector`, `array`, `string`, `span`, `optional` preconditions | MSVC 19.44 and 19.51: exit code 3221226505 (0xC0000409, `__fastfail`). MSVC 19.43: printed `0`, exit 0 |
| MSVC STL, nothing set | nothing | 19.51: `_MSVC_STL_HARDENING` is 0, printed `0`, exit 0 |
| MSVC `_ITERATOR_DEBUG_LEVEL` | a separate, ABI-breaking setting, not the hardening switch. Debug builds default to level 2 (MS STL wiki) | not run |

Notes on the rows:

- The libc++ mapping is from its Hardening documentation. FAST covers the `valid-element-access` and `valid-input-range` categories, and EXTENSIVE adds `non-null` among others. The earlier text listed `unique_ptr` and `shared_ptr` null dereference under FAST, and the documentation puts those checks in EXTENSIVE.
- libc++ hardening has no ABI impact, and the library default is none unless the vendor sets one. The earlier text called FAST the "production-default mode" and DEBUG "ABI-incompatible". The documentation says otherwise.
- The libstdc++ manual says `_GLIBCXX_ASSERTIONS` is defined by default when compiling without optimization.
- The GCC 16.2 manual lists what `-fhardened` enables (below), and says it is supported on GNU/Linux only.
- The earlier cost column (0.3%, 1-2%, 5-15%, 30-50%, 1-3%) had no source for most rows, and I removed it (not re-run on 2026-11-06).
- The libc++ 23.1.0 release notes (releases.llvm.org, read 2026-11-06) do not mention hardening modes or assertion semantics. Their one related line is an ABI note about the bounded vector and string iterators that the `_LIBCPP_ABI_BOUNDED_ITERATORS_IN_VECTOR` and `_IN_STRING` options enable. The modes are documented on the libc++ Hardening page.
- The MSVC rows used `/std:c++latest /O2`. I tested 19.43 (VS 2022 17.13), 19.44 (17.14) and 19.51. The MS STL wiki says the setting was planned as off by default with a later change to on; on 19.51 it was still 0.

The flags that `-fhardened` enables on GCC 16.2, per its manual:

```
-D_FORTIFY_SOURCE=3 -D_GLIBCXX_ASSERTIONS -ftrivial-auto-var-init=zero
-fPIE -pie -Wl,-z,relro,-z,now -fstack-protector-strong
-fstack-clash-protection -fcf-protection=full   (the last on x86 GNU/Linux only)
```

In my run, libstdc++ 16.2 did not route its hardened check through the contracts machinery. With `-O2 -D_GLIBCXX_ASSERTIONS -fcontracts`, the vector read aborted with the library's assertion under both `-fcontract-evaluation-semantic=ignore` and `observe`. I tested those two semantics on GCC 16.2 only, and not libc++.

### Where the standard stands

The draft says a hardened implementation evaluates hardened preconditions "with a terminating semantic" ([structure.specifications]/3.5.1, read on eel.is on 2026-11-06). That is the wording of [P3878R1](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2025/p3878r1.html). The paper argues that an implementation using `observe` is not hardened. libc++ documents the same risk for its own `observe` semantic. Continuing after a failed check is undefined behavior, so the semantic is meant for the adoption period.

P4433R0 (note 6) reports that this fix was applied to C++26 at Kona in November 2025. It answers the claim in P4334R0 that contracts are not appropriate for hardened libraries. The two papers disagree, and I take no side. I tested nothing beyond the runs above.

The draft's feature-test macro for hardened vector, `__cpp_lib_hardened_vector`, was defined by libstdc++ trunk (`202502`) in my run. GCC 16.2, libc++ 23.1.0 and MSVC STL 14.51 did not define it. I checked no other hardened macro.

### Two libstdc++ security fixes in October 2026

As of 2026-11-06, two libstdc++ fixes by Jonathan Wakely are on master and on the gcc-14, gcc-15 and gcc-16 branches, and in no point release. GCC 16.2 (7 August) is still the newest 16.x release, 15.3 (12 June) the newest 15.x and 14.4 (26 June) the newest 14.x. I read the commits and not the trackers.

- CVE-2026-114691, titled "Fix overflow in `std::vector<bool>` constructors" ([master commit](https://github.com/gcc-mirror/gcc/commit/2fd8866591), authored 26 October). Some constructors pass a user-provided size to `_S_nword`, which adds to find the number of words. A size close to `SIZE_MAX` wraps to zero. The fix adds a function that checks against `max_size()` and rejects negative and out-of-range values first.
- CVE-2026-114690, titled "Fix buffer overrun in `__gnu_parallel` search" ([master commit](https://github.com/gcc-mirror/gcc/commit/c1f32b6751), authored 21 October). Parallel mode, enabled by `_GLIBCXX_PARALLEL` or by including its headers, declares an array of N elements where the search needs N+1. The parallel `std::search` writes out of bounds.

The branch commits are dated 29 October. A practice follows, that code taking a size from untrusted input compares it with `max_size()` before constructing, and rebuilds against fixed headers once a release carries them. That practice is my inference, not the commits'. I did not read the trackers, their CVSS scores or the report provenance, and I did not run a reproducer (not re-run on 2026-11-06).

### What P3471R4 says about deployment

[P3471R4](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2025/p3471r4.html) (14 February 2025) says in its section on deployment experience that its authors have deployed hardening on Apple platforms in several existing code bases. It also says Google "recently published an article where they describe their experience with deploying this very technology to hundreds of millions of lines of code. They reported a performance impact as low as 0.3% and finding over 1000 bugs, including security-critical ones."

Three things from the earlier version of this page are not in the paper: "0.3% on average", "no regressions reported" and "now Google's default for new C++ builds". I removed them. The paper's authors also say the library checks only a minimal set that suits production, and that checking all preconditions is an explicit non-goal.

"As low as" makes the figure a floor from one organisation's workloads, not a prediction for yours. Measure your own. I did not measure overhead on 2026-11-06.

## Reflection today (C++26, clang-p2996 and GCC 16.2)

The hardened library protects you when you use its containers. It cannot protect a raw `int*` or `char[64]` field, because those types give the library nothing to intercept. Reflection closes the gap at the schema layer with a consteval predicate that walks the data members and refuses to compile when a field has a shape the hardened library cannot reach:

```cpp
template <typename T>
consteval bool meets_hardened_field_shapes() {
    constexpr auto ctx = std::meta::access_context::unchecked();
    template for (constexpr auto m
                  : std::define_static_array(
                      std::meta::nonstatic_data_members_of(^^T, ctx))) {
        using FieldT = [:std::meta::type_of(m):];
        static_assert(!std::is_pointer_v<FieldT>,
            "hardened-stdlib check: raw-pointer member -- use std::span "
            "or std::unique_ptr so the library's checks apply at access");
        static_assert(!std::is_array_v<FieldT>,
            "hardened-stdlib check: C-array member -- use std::array<T,N> "
            "or std::span; raw [N] has no bounds-check hook");
    }
    return true;
}

struct Frame {
    std::uint16_t           id;
    std::vector<std::byte>  payload;       // hardened-stdlib protected
    std::string             tag;           // hardened-stdlib protected
    std::span<const int>    samples;       // hardened-stdlib protected
    std::array<std::byte,4> trailer;       // hardened-stdlib protected
};

static_assert(meets_hardened_field_shapes<Frame>());
```

Replace `payload` with `std::byte* payload;` and the build fails. On GCC 16.2 the message reads:

```
error: static assertion failed: hardened-stdlib check: raw-pointer member -- use std::span or std::unique_ptr so the library's checks apply at access
  • '!(bool)std::is_pointer_v<std::byte*>' evaluates to false
```

A `char name[64]` field fails the C-array check in the same way. The diagnostic names the field type and the instantiated struct (`[with T = FrameBadPtr]`), not the field. The earlier text said it names the field, which was wrong.

## Where this is heading (C++29)

Three directions extend the hardened story. All three are papers, and I did not re-check their schedules on 2026-11-06.

Safety profiles: [P3081R2](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2025/p3081r2.pdf) (Sutter, "Core safety profiles for C++26"), [P3589R1](https://isocpp.org/files/papers/P3589R1.pdf) (Dos Reis, the framework) and [P3984R0](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/p3984r0.pdf) (Stroustrup, a type-safety profile). P3589R1 defines `[[profiles::enforce]]` and names a hardened-library profile in its examples. If profiles are adopted, a language-level check could replace the lint above. <PostLink slug="profiles-p4415-implementation-status">The 31 October post</PostLink> covers the two experimental implementations that P4415R0 reports.

Contracts: the hardened library is specified on top of contract violations, and the semantic rule above ties it to the dispute. See [the contracts page](/toolset/contracts-2026/), which also records that libstdc++ 16.2 does not route its checks through the contracts handler.

Token injection: [P3294R2](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2024/p3294r2.html) (Alexandrescu, Revzin and Vandevoorde) proposes code injection. Compiler Explorer lists no P3294 build. The earlier text suggested it could generate checked accessors, which is my speculation, not something the paper claims.
