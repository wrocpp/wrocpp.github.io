Contracts are the most disputed feature of C++26. WG21 approved the draft at Croydon on 28 March with 114 votes for, 12 against and 3 abstaining, and Stroustrup [opposed the design](https://www.devclass.com/development/2026/04/01/contracts-are-in-c26-despite-disquiet-over-their-value/5213555). The ISO ballot on that draft closed on 22 October according to P4433R0, and two named people report that it was disapproved. This page takes no side. It records what GCC 16.2 does with contracts and what I re-ran on 2026-11-06.

## In short

- As of 2026-11-06, contracts are in the C++26 working draft, not in a ratified standard. The ballot closed on 22 October and was reported disapproved, with no WG21 or ISO document stating the tally. See <PostLink slug="c26-dis-ballot-result">the ballot post</PostLink> and <PostLink slug="contracts-dispute">the dispute post</PostLink>. WG21 meets in Búzios on 16 to 21 November.
- GCC 16.2 (7 August) accepts four semantic spellings: `ignore`, `observe`, `enforce` and `quick_enforce`. It rejects `ignored` and `observed`, which the 16.2.0 manual still lists.
- Clang 23.1.0 and trunk reject `-fcontracts`, and MSVC 19.51 rejects the syntax. Prototype Clang builds exist on Compiler Explorer.
- Two samples on the earlier version of this page did not compile: a by-value parameter named in a `post` must be `const`. A third, `save_user`, compiles only if `is_connected()` is a `const` member, because a predicate sees its names as `const`.
- libstdc++ 16.2 hardening aborts through the library's own assertion, whatever contract semantic you pass. I tested `ignore` and `observe`.

## Today

### The three assertion kinds

P2900R14 adds three contract annotations to C++26:

```cpp
int f(int i)
    pre(i >= 0)                    // precondition: checked before entry
    post(r: r > 0)                 // postcondition: checked after return
{
    contract_assert(i < 1000);     // mid-function assertion
    return i + 1;
}
```

`pre(condition)` is evaluated before the function body. Several `pre` specifiers are allowed, and they are evaluated in the order declared (P2900R14, section 3.5.1).

`post(r: condition)` is evaluated after the function returns. The identifier before the colon names the result.

`contract_assert(condition)` replaces `assert()` inside function bodies. The compiler flag controls whether it is checked. With `-DNDEBUG -O2` on GCC 16.2 a violated `contract_assert` still fired (`assertion_kind: assert, semantic: enforce`).

`pre` and `post` are context-sensitive keywords that follow the declarator. `contract_assert` is a full keyword. This version compiles and runs on GCC 16.2 and trunk (`-std=c++26 -fcontracts`):

```cpp
std::string normalize(const std::string_view input)
    pre(!input.empty())
    pre(input.size() <= max_input_size)
    post(result: !result.empty())
    post(result: result.size() <= input.size())
{
    contract_assert(is_valid_encoding(input));
    return std::string{input};
}
```

Lambdas work too:

```cpp
auto safe_div = [](const int a, const int b)
    pre(b != 0)
    post(r: r * b == a || a % b != 0)
{
    return a / b;
};
```

Both samples declare their by-value parameters `const`, and that is required. An earlier version of this page omitted it, and GCC 16.2 rejects that form:

```
error: a value parameter used in a postcondition must be const
```

P2900R14 section 3.4.4 states the rule. A parameter used in a `post` must be a reference or `const` on every declaration, including the definition.

Names in a predicate are const. Section 3.4.2 makes every name from outside the predicate a `const` lvalue, including parameters, members and `*this`. The constness is shallow: an object reached through a pointer is not `const`. A non-`const` member function called on a reference parameter is therefore an error:

```
error: passing 'const Database' as 'this' argument discards qualifiers [-fpermissive]
```

Virtual functions: contract specifiers on a virtual function are ill-formed (section 3.3.2), and GCC 16.2 says `error: contracts cannot be added to virtual functions`. The paper expects a later proposal to change that.

Redeclarations: a redeclaration must repeat the same specifiers or omit them (section 3.3.1). Adding contracts on a later declaration is an error on GCC 16.2: `error: declaration adds contracts to 'int f(int)'`. First declarations with different specifiers in different translation units are ill-formed, no diagnostic required.

### The four evaluation semantics

The semantic is chosen per translation unit at compile time, not per assertion in the source:

| Semantic | Predicate evaluated? | Handler called? | Program terminates? | GCC 16.2, run 2026-11-06 |
|----------|---------------------|-----------------|--------------------|----|
| `ignore` | No | No | No | predicate must still compile; a counter in the predicate stayed 0 |
| `observe` | Yes | Yes | No (continues) | handler output, then the program continued, exit 0 |
| `enforce` | Yes | Yes | Yes (after handler) | the default; handler output, then `std::terminate`, SIGABRT |
| `quick_enforce` | Yes | No | Yes | no handler output; `std::terminate`, SIGABRT |

- `ignore`: the predicate is not evaluated but must still compile. An undeclared name in it is an error (`'i_misspelled' was not declared in this scope`).
- `observe`: the handler runs, then execution continues past the violation. This is the mode for introducing contracts into an existing code base, because violations appear in logs without crashes.
- `enforce`: the handler runs, then the program terminates. A handler that throws escapes termination when the function is not `noexcept`. I tested that on GCC 16.2 under `enforce` and `observe`: the exception was caught.
- `quick_enforce`: the program terminates without calling the handler. The earlier version of this page said this is "typically `__builtin_trap()`". On GCC 16.2 it is not: the run printed `terminate called without an active exception` and ended with SIGABRT at `-O0` and `-O2`.

The `observe` output of the default handler looks like this:

```
contract violation in function int divide(int, int) at /app/example.cpp:3: b != 0
[assertion_kind: pre, semantic: observe, mode: predicate_false, terminating: no]
```

### Compiler flags

GCC 16.1 shipped on 30 April 2026 and GCC 16.2 on 7 August 2026. These lines were run on 16.2:

```bash
# Enable contracts; enforce is the default semantic
g++ -std=c++26 -fcontracts main.cpp

# Observe mode (log violations, continue)
g++ -std=c++26 -fcontracts -fcontract-evaluation-semantic=observe main.cpp

# Quick-enforce mode (terminate without the handler)
g++ -std=c++26 -fcontracts -fcontract-evaluation-semantic=quick_enforce main.cpp

# Ignore all contracts (predicates still must compile)
g++ -std=c++26 -fcontracts -fcontract-evaluation-semantic=ignore main.cpp
```

Only those four spellings are valid. The GCC 16.2.0 manual (C++ Dialect Options) lists `ignored` and `observed`, and an earlier version of this page copied them. GCC 16.2 and trunk reject them:

```
g++: error: unrecognized contract evaluation semantic 'observed'
g++: note: valid arguments to '-fcontract-evaluation-semantic=' are: enforce ignore observe quick_enforce; did you mean 'observe'?
```

With `-std=c++26` alone, GCC defines `__cpp_contracts` as `202502` and parses the syntax. A program with a contract check then fails to link on GCC 16.1, 16.2 and trunk: `undefined reference to handle_contract_violation(std::contracts::contract_violation const&)`. With your own handler, GCC 16.2 links and runs it without `-fcontracts`. Pass the flag.

Clang: Clang 23.1.0 and Clang trunk on Compiler Explorer reject the flag (`clang++: error: unknown argument: '-fcontracts'`). Compiler Explorer lists prototype builds with P2900 contracts, among them `clang_ericwf_contracts`, which [contracts.efcs.ca](https://contracts.efcs.ca/) documents. Its flags are `-fcontracts -stdlib=libc++` and the same four semantic values. I ran only that build, and it reported `post(r: r > 0) failed` for a call returning 4, so treat it as a prototype. The repository this page used to link, `arcosuc3m/clang-contracts` (now `jdgarciauc3m/clang-contracts`), is a 2017 LLVM snapshot with a prototype of P0542R5, not P2900. I removed the link.

MSVC: MSVC 19.51 (14.51.36246, `/std:c++latest`) rejects the syntax. Its errors include `error C2760: syntax error: 'pre' was unexpected here; expected '{'`.

### The replaceable violation handler

When a contract is violated under `observe` or `enforce`, the implementation calls:

```cpp
void handle_contract_violation(
    const std::contracts::contract_violation& v);
```

P2900R14 (section 3.7.3) and libstdc++ 16.2 do not use the same names:

| P2900R14 member | libstdc++ 16.2 | Description |
|--------|---------|-------------|
| `kind()` | `kind()` | `assertion_kind`: `pre`, `post` or `assert` |
| `semantic()` | `semantic()` | which semantic was active |
| `location()` | `location()` | `std::source_location` |
| `comment()` | `comment()` | text of the predicate (implementation-defined) |
| `is_terminating()` | `is_terminating()` | whether the program terminates after the handler |
| `detection_mode()` | `mode()` | `predicate_false` or `evaluation_exception` |
| `evaluation_exception()` | absent | the exception, if the predicate threw |

The libstdc++ names come from its 16.2.0 header. I compiled and ran six of the accessors on GCC 16.2: all but the absent one. Replace the handler the way you replace `operator new`, by defining your own:

```cpp
#include <contracts>
#include <cstdio>
#include <print>

void handle_contract_violation(
    const std::contracts::contract_violation& v)
{
    std::println(stderr, "[CONTRACT] {} violated at {}:{}  predicate: {}",
        v.kind() == std::contracts::assertion_kind::pre ? "pre" :
        v.kind() == std::contracts::assertion_kind::post ? "post" : "assert",
        v.location().file_name(),
        v.location().line(),
        v.comment());
}
```

This handler compiled and ran on GCC 16.2. Under `observe` it returned and the program continued. Under `enforce` it returned and `std::terminate` ran. Under `quick_enforce` it was not called.

### Practical patterns

The next four sketches show where contracts go. They stand in for your own types. I compiled and ran the first one on GCC 16.2 with small definitions for the user types. The other three were not compiled.

Module boundaries: put contracts on public API functions:

```cpp
// public_api.h
namespace mylib {

std::expected<User, Error> parse_user(std::string_view json)
    pre(!json.empty())
    pre(json.size() <= max_json_size)
    post(r: r.has_value() || r.error() != Error::none);

void save_user(const User& u, Database& db)
    pre(u.id > 0)
    pre(db.is_connected());   // is_connected() must be a const member

} // namespace mylib
```

Serialization: validate parsed values before struct population:

```cpp
template <typename T>
T deserialize(std::span<const std::byte> data)
    pre(data.size() >= sizeof(uint32_t))
{
    auto header = read_header(data);
    contract_assert(header.version <= current_version);
    contract_assert(header.payload_size <= data.size() - sizeof(header));
    return decode<T>(data.subspan(sizeof(header)));
}
```

FFI boundaries: catch invalid arguments before they cross into C or system calls:

```cpp
int safe_write(int fd, const void* buf, size_t count)
    pre(fd >= 0)
    pre(buf != nullptr || count == 0)
    pre(count <= max_write_size)
{
    return ::write(fd, buf, count);
}
```

Contracts as fuzz oracles: the contract can serve as the test oracle:

```cpp
// Step 1: annotate the function
Json parse_json(std::string_view input)
    pre(input.size() <= max_input);

// Step 2: write the fuzz harness (no oracle needed)
extern "C" int LLVMFuzzerTestOneInput(const uint8_t* data, size_t size) {
    auto input = std::string_view(reinterpret_cast<const char*>(data), size);
    try {
        auto result = parse_json(input);  // contracts check automatically
    } catch (...) {}
    return 0;
}
```

Under `enforce` a violation ends in `std::terminate`, which GCC 16.2 reports as SIGABRT, and a fuzzer sees that as a crash. I did not run this pattern (not re-run on 2026-11-06). libFuzzer needs Clang, and Clang 23.1.0 does not accept `-fcontracts`. I dropped `post(r: r.is_valid())` and `post(r: r.is_well_formed())` from the samples on this page. A `post` that calls a member function on a class-type result crashed GCC at `-O0` in this reproducer, and I did not test your types:

```cpp
struct Result { bool is_valid() const { return true; } };
Result make() post(r: r.is_valid()) { return Result{}; }
// g++ -std=c++26 -fcontracts -O0 (GCC 16.2.0 and trunk 20261106):
// internal compiler error: in expand_expr_addr_expr_1, at expr.cc:9318
```

The same program compiles at `-O2`, and a `std::expected` result with `r.has_value()` compiled at `-O0`. The ICE location matches [GCC bug 125574](https://gcc.gnu.org/bugzilla/show_bug.cgi?id=125574), which was unconfirmed when I looked.

### Migration strategy

Contracts reward a staged rollout:

1. Observe in staging. Compile your test suite and canary deployments with `-fcontract-evaluation-semantic=observe`. Violations are logged and the program continues. Gather data on which contracts fire.
2. Triage. Fix real bugs found by violations. Weaken contracts that are too strict, and remove contracts that are wrong.
3. Enforce in production. Once the violation rate in staging is zero, switch to `enforce`. Violations now terminate the program.
4. Use `quick_enforce` where you do not want the handler to run.

libc++ documents a similar use of `observe` for its hardening checks. It is meant to ease adoption and "should not be used outside of the adoption period", because continuing after a failed hardening check is undefined behavior (libc++ Hardening documentation).

The draft goes further for the standard library. A hardened implementation evaluates hardened preconditions with a terminating semantic ([structure.specifications]/3.5.1, the wording P3878R1 proposed). See [hardened-stdlib](/toolset/hardened-stdlib/).

The semantic is chosen by whoever configures the build, not by whoever wrote the function. <PostLink slug="cpp26-contracts">That post</PostLink> covers the consequence.

## Reflection today (C++26)

### Can reflection see contracts?

No. Neither the C++26 draft's `<meta>` synopsis (eel.is/c++draft/meta.syn, read 2026-11-06) nor libstdc++ 16.2's `<meta>` header has a facility for contract specifiers. There is no `std::meta::contracts_of`. `std::meta::nonstatic_data_members_of` walks struct fields, and contract specifiers are properties of declarations.

You cannot write a reflection-driven "verify all public functions have contracts" lint today. The check must come from external tooling or code review.

### How contracts compose with reflection patterns

Contracts and reflection compose at the application level. The serialization functions from posts <PostLink slug="json-naive">8</PostLink> to <PostLink slug="one-codegen-many-formats">11</PostLink> generate field-walking code at compile time. A `pre()` or `post()` on the generated function's declaration checks invariants for every reflected field:

```cpp
template <typename T>
std::string to_json(const T& obj)
    post(r: !r.empty())
    post(r: r.front() == '{')
{
    // reflection-generated field walk
}
```

With a trivial body that returns `"{}"`, these two postconditions compiled and ran on GCC 16.2 at `-O0` and `-O2`. The ICE above involved a user-defined result type, and I did not test your types.

Contracts and sanitizers differ in what they check and what they cost. I measured none of the costs on 2026-11-06 (not re-run on 2026-11-06). The sources are:

| Mechanism | What it catches | Cost data |
|-----------|-----------------|-----------|
| Contracts | Violated specifications you wrote | one check per assertion; not measured here |
| Hardened stdlib (P3471) | OOB access, null dereference, overruns in library calls | P3471R4 cites Google: a performance impact "as low as 0.3%" |
| ASan | Heap and stack buffer overflow, use-after-free | Clang documents a typical slowdown of 2x |
| UBSan | Signed overflow, alignment, shift | no figure in the Clang documentation; depends on the checks enabled |

See [sanitizers-2026](/toolset/sanitizers-2026/) for the sanitizer matrix.

## Where this is heading

### C++29 directions

Virtual function contracts: P2900R14 says support for `pre` and `post` on virtual functions is "expected to be proposed in a future extension" (section 3.3.2). The open question is whether a derived class may weaken a precondition or strengthen a postcondition.

Contracts and profiles: [P3589R1](https://isocpp.org/files/papers/P3589R1.pdf) (Dos Reis, 2 February 2025) defines the profiles framework: `[[profiles::enforce]]`, `[[profiles::require]]` and `[[profiles::suppress]]`. I read it on 2026-11-06 and it does not mention contracts. An earlier version of this page said profiles would use contracts as their enforcement substrate. The paper does not say that, and I removed the claim. <PostLink slug="profiles-p4415-implementation-status">The 31 October post</PostLink> covers the two experimental profile implementations that P4415R0 reports; I did not re-run them on 2026-11-06.

Code injection (P3294): token injection could in principle generate contracts from annotations. This sketch is pseudo-code that no compiler accepts, and Compiler Explorer lists no P3294 build:

```cpp
// pseudo-code, not C++ any compiler accepts today
template <typename T>
consteval void inject_range_contracts(std::meta::info fn) {
    for (auto param : std::meta::parameters_of(fn)) {
        if (has_annotation<bounded>(param)) {
            auto [lo, hi] = annotation_of<bounded>(param);
            // inject: pre(param >= lo && param <= hi)
        }
    }
}
```

### The bigger picture

| Layer | Standard | Status on 2026-11-06 |
|-------|----------|--------|
| Contracts (P2900) | C++26 draft | GCC 16.1 and later behind `-fcontracts`; the draft was reported disapproved in the ballot |
| Hardened stdlib (P3471) | C++26 draft | macros in libstdc++, libc++ and the MSVC STL, tested on [its page](/toolset/hardened-stdlib/) |
| Erroneous behavior (P2795R5) | C++26 draft | listed in the GCC 16 changes; not re-run on 2026-11-06 |
| Profiles | after C++26 | framework paper P3589R1; two experimental implementations per P4415R0; not re-run |
| Code injection (P3294) | after C++26 | no build on Compiler Explorer |

Whether these layers form a stack depends on decisions WG21 has not made. The <PostLink slug="cpp-safety-state-of-the-union-may-2026">May safety essay</PostLink> documents the gap they are meant to close.
