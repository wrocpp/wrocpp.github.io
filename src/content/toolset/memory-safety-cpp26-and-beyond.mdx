Hardening, contracts and reflection are in the C++26 working draft that WG21 approved at Croydon in March 2026 ([Sutter's trip report](https://herbsutter.com/2026/03/29/c26-is-done-trip-report-march-2026-iso-c-standards-meeting-london-croydon-uk/)). The `[[profiles::enforce]]` attribute is not in that draft. It targets C++29. This page separates what the draft contains, what moved to C++29, and what you can switch on today with the exit codes I measured.

## In short

- As of 2026-11-06 the C++26 draft is not a published standard. Its ISO ballot closed on 22 October and was reported disapproved by Seacord, Pusz and Fertig. No WG21 or ISO document states the tally. See <PostLink slug="c26-dis-ballot-result">the ballot post</PostLink> and <PostLink slug="contracts-dispute">the contracts dispute</PostLink>.
- The hardening switches below all stop a `vector` out-of-bounds read on GCC 16.2, Clang 23.1.0 and MSVC 19.51. The exit codes differ, and only libstdc++ and libc++ `DEBUG` print a message.
- libc++ 23.1.0 did not stop a null `unique_ptr` dereference at any hardening mode I tried. libstdc++ with `_GLIBCXX_ASSERTIONS` did for `operator*`.
- Two snippets on the earlier version of this page were wrong. `[[clang::lifetimebound]]` goes on a parameter, and GCC 16.2 does implement contracts behind `-fcontracts`.
- Profiles now have two experimental compiler forks on Compiler Explorer. No released compiler has them.

As of 2026-11-06. The ballot, the Búzios meeting (16 to 21 November) and the profile papers of 22 October change the C++29 section most. The recommendations in "What you can switch on today" did not change, apart from the corrections listed above.

#### Hardened standard library (P3471)

This is the highest-leverage switch and needs no change at call sites. P3471R4 cites Google's deployment of hardened libc++ with a cost as low as 0.3% and over 1000 bugs found. Treat that as Google's report, not as a number you will see.

Three implementations, three settings:

```bash
# libc++ (Clang)
-D_LIBCPP_HARDENING_MODE=_LIBCPP_HARDENING_MODE_FAST       # security-critical checks only
-D_LIBCPP_HARDENING_MODE=_LIBCPP_HARDENING_MODE_EXTENSIVE  # adds cheap logic-error checks
-D_LIBCPP_HARDENING_MODE=_LIBCPP_HARDENING_MODE_DEBUG      # adds expensive checks

# libstdc++ (GCC)
-D_GLIBCXX_ASSERTIONS         # lightweight precondition checks
-fhardened                    # umbrella: includes the assertions; GNU/Linux only
-D_GLIBCXX_DEBUG              # heavy, ABI-breaking, catches iterator invalidation

# MSVC STL
_MSVC_STL_HARDENING=1         # off by default; fastfail on violation
_ITERATOR_DEBUG_LEVEL=1       # separate and ABI-breaking; not the hardening switch
```

What I ran on 2026-11-06, one `vector<int>` of three elements read at index `argc + 5`, at `-O1`:

| Toolchain and setting | Exit | Output |
|---|---|---|
| g162, no setting | 0 | a garbage value |
| g162 `-D_GLIBCXX_ASSERTIONS` | 134 (SIGABRT) | the assertion, with file and line of `stl_vector.h` |
| g162 `-fhardened` | 134 (SIGABRT) | the same assertion |
| clang2310 libc++ `FAST` | 132 (SIGILL) | nothing |
| clang2310 libc++ `EXTENSIVE` | 132 (SIGILL) | nothing |
| clang2310 libc++ `DEBUG` | 134 (SIGABRT) | `vector[] index out of bounds` |
| vcpp_v19_latest_x64 `/D_MSVC_STL_HARDENING=1` | 3221226505 (0xC0000409) | nothing |

With `-fhardened -D_GLIBCXX_ASSERTIONS` together GCC warns that `-fhardened` does not enable the assertions because you defined them yourself. The vector read still aborted. The [hardened-stdlib](/toolset/hardened-stdlib/) page records that libstdc++ assertions print and abort without going through the contracts handler, tested there with `ignore` and `observe`. I did not repeat that test here.

##### Null unique_ptr

A null `unique_ptr` is where the libraries differ. With `_GLIBCXX_ASSERTIONS`, `*p` aborted with SIGABRT at `-O0`. On Clang 23.1.0 with libc++, a null dereference ended in SIGSEGV at `-O0`. That held with no setting, with `FAST` and with `EXTENSIVE`, for both `*p` and `p->x`. It also held with `DEBUG`, tested for `*p` only. So I would not tell anyone that libc++ hardening catches a null `unique_ptr` dereference. I did not test `operator[]` of `unique_ptr<T[]>` or `shared_ptr`.

##### Setting it in CMake

CMake snippet that sets the setting explicitly:

```cmake
if(CMAKE_CXX_COMPILER_ID STREQUAL "Clang" OR
   CMAKE_CXX_COMPILER_ID STREQUAL "AppleClang")
    add_compile_definitions(
        _LIBCPP_HARDENING_MODE=_LIBCPP_HARDENING_MODE_FAST
    )
elseif(CMAKE_CXX_COMPILER_ID STREQUAL "GNU")
    add_compile_options(-fhardened)   # also pass it when linking
elseif(CMAKE_CXX_COMPILER_ID STREQUAL "MSVC")
    add_compile_definitions(_MSVC_STL_HARDENING=1)
endif()
```

libstdc++ also fixed two library bugs in October: CVE-2026-114691 (`vector<bool>` constructors) and CVE-2026-114690 (parallel `std::search`). The fixes are on the gcc-14, gcc-15 and gcc-16 branches and in no point release as of 2026-11-06. The [hardened-stdlib](/toolset/hardened-stdlib/) page has the details. For more, see [libc++'s hardening documentation](https://libcxx.llvm.org/Hardening.html), its [known gap for vector iterators (LLVM #128627)](https://github.com/llvm/llvm-project/issues/128627), and the [OpenSSF Compiler Options Hardening Guide](https://best.openssf.org/Compiler-Hardening-Guides/Compiler-Options-Hardening-Guide-for-C-and-C++.html).

A hardened library is only as strong as its terminating behaviour. P3878R1, applied to the draft at Kona in November 2025, says an implementation should not count as hardened if it evaluates hardened preconditions with the `observe` semantic (P4433R0, note 6). I did not test what that means for libstdc++ 16.2, which aborts through its own assertion on this build.

#### clang-tidy `cppcoreguidelines-pro-*` checks

The "Pro" prefix in these clang-tidy checks stands for profile: they implement the Core Guidelines bounds and type profiles in a static analyzer. All ten names below are listed by `clang-tidy --checks='*' --list-checks` in clang-tidy 23.1.1 (run on 2026-11-06). I did not run them on a sample project. clang-tidy analyses the source, so it works whichever compiler builds the code.

```yaml
# .clang-tidy fragment for a sample bounds + type profile gate
Checks: >
  cppcoreguidelines-pro-bounds-pointer-arithmetic,
  cppcoreguidelines-pro-bounds-constant-array-index,
  cppcoreguidelines-pro-bounds-array-to-pointer-decay,
  cppcoreguidelines-pro-bounds-avoid-unchecked-container-access,
  cppcoreguidelines-pro-type-cstyle-cast,
  cppcoreguidelines-pro-type-reinterpret-cast,
  cppcoreguidelines-pro-type-static-cast-downcast,
  cppcoreguidelines-pro-type-member-init,
  cppcoreguidelines-pro-type-union-access,
  cppcoreguidelines-pro-type-vararg
WarningsAsErrors: '*'
```

Tune the disable list for C-API boundaries. Pointer arithmetic on a `char*` from a C library is unavoidable in some adapters, and turning the check on without exemptions produces noise. The official check list lives at [clang.llvm.org/extra/clang-tidy/checks/list.html](https://clang.llvm.org/extra/clang-tidy/checks/list.html).

#### MSVC Lifetime Profile via `/analyze`

Sutter's original Lifetime Profile has had a partial MSVC implementation since 2018, by Neil MacIntosh and Kyle Reed. It runs in MSVC's static analyzer and catches a subset of dangling-pointer and use-after-scope cases. Enable it with `/analyze`, or `/analyze:plugin EspXEngine.dll` for the Code Analysis variant. It is not standard and not portable. Not re-run on 2026-11-06, so this paragraph is the page's earlier text.

The Clang side had an experimental `-Wlifetime` fork by Matthias Gehre and Gábor Horváth ([mgehre/llvm-project](https://github.com/mgehre/llvm-project)). The repository is archived and its last push was on 2021-07-14.

#### `[[clang::lifetimebound]]` and `[[gnu::access]]` attributes

Both are narrow and deployable. `[[clang::lifetimebound]]` goes on a parameter, or on the implicit object parameter of a member function. It says the returned reference or view is bound to that argument, and Clang then warns when the argument is a temporary.

```cpp
// Clang 23.1.0 -Wall: warning: temporary bound to local reference 'r'
// will be destroyed at the end of the full-expression [-Wdangling]
const std::string& pick(const std::string& s [[clang::lifetimebound]]) { return s; }
const std::string& r = pick(std::string("temporary"));
```

The earlier version of this page put the attribute in front of the function. Clang 23.1.0 rejects that with "'clang::lifetimebound' attribute only applies to parameters and implicit object parameters". GCC 16.2 accepts the source and ignores the attribute with a `-Wattributes` warning.

`[[gnu::access]]` is a different tool: a size hint for GCC's buffer analysis, not a lifetime attribute. Both spellings below warned on g162 at `-Wall -O2` when I called `fill` with a two-element array and a count of five (`writing 20 bytes into a region of size 8`):

```cpp
void fill(int* buf, size_t n) [[gnu::access(write_only, 1, 2)]];
__attribute__((access(write_only, 1, 2))) void fill(int* buf, size_t n);
```

Clang 23.1 also has a `-Wlifetime-safety` warning family. The [lifetime-safety-2026](/toolset/lifetime-safety-2026/) page covers it.

#### Contracts (P2900)

Contracts are `pre` and `post` clauses on declarations plus `contract_assert` in bodies. They have four evaluation semantics: `ignore`, `observe`, `enforce` and `quick_enforce`. They are in the C++26 draft, and the ballot dispute above is about them. What compilers do, as run on 2026-11-06:

- GCC 16.2: `-std=c++26 -fcontracts` works. A violated `pre(x > 0)` printed the violation with `semantic: enforce` and ended in SIGABRT (exit 134). The earlier claim that GCC "emits warnings only" was wrong.
- Clang 23.1.0, `clang_bb_p2996`: both reject `-fcontracts` and `-fcontracts=enforce` as unknown arguments. The earlier claim about `-fcontracts=enforce` on clang-p2996 was wrong.
- MSVC 19.51: rejects the syntax, per the [contracts-2026](/toolset/contracts-2026/) page.

The hardened standard library (P3471) is specified in terms of contract assertions, which is the link to the dispute. On libstdc++ 16.2 the hardening checks abort through the library's own assertion. For application-side preconditions, state the invariant once on the function and pick a semantic per translation unit.

### What regulated industries do today

For automotive, aerospace and medical software the language standard alone has never been enough. The [cpp-coding-standards](/toolset/cpp-coding-standards/) page has the detail and the corrections to the rule labels; the short form:

- MISRA C++:2023 targets C++17 and was published in October 2023, per [misra.org.uk](https://misra.org.uk/misra-cpp2023-released-including-hardcopy/). It integrates the AUTOSAR C++14 guidelines, following the [2019 announcement by MISRA and AUTOSAR](https://www.autosar.org/news-events/detail/misra-consortium-announce-integration-of-autosar-c-coding-guidelines-into-updated-industry-standard). I found no primary source for a guideline count, so this page gives none.
- SEI CERT C++ is a free, web-published secure-coding standard. clang-tidy's `cert-*` checks cover part of it.
- C++ Core Guidelines are cited by most of the others. clang-tidy's `cppcoreguidelines-*` checks cover part of them.

When profiles arrive in a future standard, some of these rules may become language-level guarantees. Nothing in the C++26 draft does that.


## Reflection today (C++26, GCC 16.2 and the Bloomberg Clang fork)

For per-class structural rules ("no raw pointer members", "no C-style arrays", "all members trivially copyable"), C++26 reflection lets a user library enforce profile-like constraints today without waiting for the C++29 attribute. On 2026-11-06 the source below ran on `clang_bb_p2996` and, with `<meta>` in place of `<experimental/meta>` and `-std=c++26 -freflection`, on GCC 16.2 and trunk. The pattern: a `consteval` predicate that walks the class's data members and `static_assert`s on each one. Add a forbidden member type, the build refuses; remove it, the build proceeds.

```cpp
template <typename T>
consteval bool meets_basic_safety_profile() {
    constexpr auto ctx = std::meta::access_context::unchecked();
    template for (constexpr auto m
                  : std::define_static_array(
                      std::meta::nonstatic_data_members_of(^^T, ctx))) {
        using FieldT = [:std::meta::type_of(m):];
        static_assert(!std::is_pointer_v<FieldT>,
                      "safety profile violation: raw pointer member");
        static_assert(!std::is_array_v<FieldT>,
                      "safety profile violation: C-style array member");
    }
    return true;
}

struct GoodSession {
    std::string                username;
    std::vector<std::byte>     buffer;
    std::unique_ptr<int>       counter;
    std::array<std::byte, 16>  tag;
};

static_assert(meets_basic_safety_profile<GoodSession>());
```

Uncomment `BadSessionRawPtr` and both compilers fail the build. GCC 16.2 prints `static assertion failed: safety profile violation: raw pointer member`. The `BadSessionCArr` case fails the same way with `C-style array member`. The message comes from a user library, not from the language.

### Which rules it maps to

What this aligns with:

- C++ Core Guidelines [I.11](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#Ri-raw) (never transfer ownership by raw pointer), [F.7](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#Rf-smart) / [F.20](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#Rf-out) / [F.43](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#Rf-dangle) (ownership rules), [ES.42](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#Res-ptr) (keep use of pointers simple).
- MISRA C++:2023 (the unified MISRA + AUTOSAR successor) prohibitions on raw pointer arithmetic and unbounded C arrays at the API level. The reflection-driven check enforces the equivalent rule one class at a time, by construction.
- SEI CERT C++ STR (string-handling) and MEM (memory-management) categories converge on the same property: typed access at the boundary, no raw-pointer gymnastics.

What this user-library check does NOT solve:

- Function-body checks such as "no raw pointer arithmetic *inside* a function": these need a statement-level mechanism such as a profile.
- Cross-translation-unit checks (e.g. "no callsite passes a non-`std::span` to a `[[profile-enforced]]` function"): need the language attribute and link-time tooling.
- Migration tooling: a profile attribute can carry a phased "warn-only" mode; user-library `static_assert` is binary "compiles or doesn't".

For new code at the type-shape level, the check tells you that a class has no raw pointer or C array members. Whether it would compose with `[[profiles::enforce]]` is untested, because no released compiler has the attribute.

## Where this is heading (C++29)

Per the [Croydon trip report](https://herbsutter.com/2026/03/29/c26-is-done-trip-report-march-2026-iso-c-standards-meeting-london-croydon-uk/), SG23 (Safety and Security) continues work on profiles for C++29. As of 2026-11-06 the papers are the ones in the table above. The three that define the shape are:

- [P3589R2](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2025/p3589r2.pdf) (Dos Reis), the framework. It defines the `[[profiles::enforce]]`, `[[profiles::require]]` and `[[profiles::suppress]]` attributes, and P4415R0 adds `[[profiles::exempt]]` to the list of features it measures. Opting out of one profile does not opt out of others.
- The profiles themselves. Stroustrup's [P4222R3](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/p4222r3.pdf) (initialization) and [P4418R0](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/p4418r0.pdf) (invalidation) are the two with implementations. P4415R0 names them `std::init` and `std::invalidation`.
- Evidence. [P4158R0](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/p4158r0.pdf) (Hunt) reports about 4 million lines of WebKit code under a subset, and P4415R0 reports the two forks. Neither says the approach is ready for the C++29 schedule.

The illustrative shape below uses the attribute syntax from P3589R2 and the profile names from P4415R0. It is a sketch, not code that a released compiler accepts, and the syntax may change before C++29:

```cpp
// Sketch only (P3589R2 attribute, P4415R0 profile names).
[[ profiles::enforce(std::init, std::invalidation) ]]
namespace safe_io {
    auto read(std::span<const std::byte> in) -> ParsedDoc;
    auto write(std::span<std::byte> out, const ParsedDoc&)
        -> std::expected<void, error>;
}
// Per-block opt-out would use [[profiles::suppress(...)]].
```

Token injection ([P3294](https://wg21.link/p3294), Revzin, Alexandrescu and Vandevoorde, latest revision R2 from 2024) is a separate C++29 candidate. It would let an annotation inject members as well as enforce rules:

```cpp
// Sketch only: P3294 describes code injection with token sequences; this
// attribute-driven form is an illustration, not syntax from the paper.
[[ inject(safe_api) ]]
struct SensorReading {
    std::uint16_t sensor_id;
    std::int32_t  raw_value;
    std::uint8_t  status_flags;
};
```

### Sidebar: cppfront, Sutter's design as a working compiler

For readers who want to see Sutter's original profile design *operating today*, [cppfront](https://github.com/hsutter/cppfront) is his experimental Cpp2-syntax-to-Cpp1 compiler. Cpp2 has type / bounds / initialization / lifetime safety by default: use of an uninitialized variable is statically diagnosed, container access is bounds-checked, mixed-sign comparisons and integer divide-by-zero are checked at runtime. The opposite of standard C++'s "you have to opt IN to safety" -- you opt OUT (per scope, with explicit `unchecked` or per-flag `-no-subscript-checks` etc.) when a hot path needs it.

It is not standard C++ and not a `[[profiles::enforce]]` implementation. It is Sutter's testbed for the design intent.

A 25-line Cpp2 demo runs on Compiler Explorer in tree mode: a single `test.cpp2` paired with a GCC 16.1 executor, with Compiler Explorer invoking cppfront for the `.cpp2` extension. ### How the pieces fit

Hardening catches runtime corners that compile-time analysis misses, and it is available now. Sanitizers stay in CI for legacy paths. Profiles, if they land in C++29, would enforce a subset at compile time. Which of these you rely on depends on the toolchain you ship with, and the ballot result does not change the first two.
