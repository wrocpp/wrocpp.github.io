Bounds and null have settled answers in the standard library. Lifetime does not. A function returns a `string_view` of a local `string`, a struct holds a `string_view` next to its source `string` and gets moved, a coroutine resumes after its referent is gone, and compilers diagnose these unevenly. This page records what Clang, GCC and MSVC flagged in one sample on 2026-11-06.

## In short

- As of 2026-11-06, Clang 23.1.0 (released 25 August) has `-Wlifetime-safety`, which is off by default and on in `-Weverything`. In my sample it caught a parameter escaping into a field and a temporary that dies too soon.
- `-Wlifetime` is not a mainline Clang flag. The earlier CMake recipe used it, and Clang 23.1.0 and trunk answer `unknown warning option`.
- Clang trunk renamed `-Wlifetime-safety-invalidation` to `-Wlifetime-safety-experimental-invalidation` on 2026-10-20. Clang 23.1.0 still uses the old name.
- GCC 16.2 gave no diagnostic for any of the `string_view` cases in the sample. `-Wdangling-pointer` is from GCC 12, not 13.
- No tool in the sample flagged a view that dangles after its owning struct is moved. `std::scope_exit` is not in C++26.

## Today

### What I ran

This sample has five dangling cases. It compiles without error on every compiler below.

```cpp
std::string_view pick_local() {
    std::string s = "a string long enough to defeat the small buffer";
    return s;                                  // view of a local
}
std::string_view from_param(std::string s) { return s; }   // view of a parameter

struct DanglingView {
    std::string_view view;
    DanglingView(std::string s) : view(s) {}   // parameter escapes to a field
};

struct Frame {
    std::string payload;
    std::string_view header;
    explicit Frame(std::string p) : payload(std::move(p)), header(payload) {}
};

int use_temp() {
    std::string_view sv = std::string("a temporary long enough to live on the heap");
    return static_cast<int>(sv.size());        // temporary already destroyed
}

Frame moved_frame() {
    Frame a{"a payload long enough to live on the heap, not in the buffer"};
    Frame b = std::move(a);                    // header still points into a.payload
    return b;
}
```

| Compiler and options | Flagged | Not flagged |
|---|---|---|
| Clang 23.1.0, `-Wall -Wextra` | `pick_local` and `from_param` (`-Wreturn-stack-address`), `use_temp` (`-Wdangling-gsl`) | `DanglingView`, `moved_frame` |
| Clang 23.1.0, `-Wlifetime-safety -Wlifetime-safety-suggestions` | the three above, plus `DanglingView` (`-Wlifetime-safety-dangling-field`) and `use_temp` again (`-Wlifetime-safety-use-after-scope`) | `moved_frame` |
| Clang trunk, same options, then with `-Wlifetime-safety-all -Wlifetime-safety-strict -Wlifetime-safety-dangling-field-moved` | the same as 23.1.0 | `moved_frame` |
| GCC 16.2, `-Wall -Wextra -Wdangling-reference -Wdangling-pointer` | nothing | all five |
| GCC trunk, `-Wall -Wextra` | nothing | all five |
| MSVC 19.51, `/W4 /analyze /analyze:plugin EspXEngine.dll` | `pick_local` and `from_param` (C26816), `use_temp` (C26815, C26449) | `DanglingView`, `moved_frame` |

The new Clang diagnostic for `DanglingView` reads:

```
warning: stack memory associated with parameter 's' escapes to the field 'view' which will dangle [-Wlifetime-safety-dangling-field]
```

So "structural dangling escapes every per-call analyzer" is only partly true on 2026-11-06. Clang 23.1 catches the parameter-to-field case. The moved-struct case, where the view still points into the moved-from `payload`, was caught by none of them.

GCC's two warnings do fire on the cases they were written for. With `-O2`, `const int& r = std::max(1, 2);` gave `warning: possibly dangling reference to a temporary [-Wdangling-reference]`, and a pointer to a block-scope variable used after the block gave `using dangling pointer 'p' to 'x' [-Wdangling-pointer=]`. They did not fire on any `string_view` conversion above. GCC's manual puts both warnings in `-Wall`. `-Wdangling-pointer` arrived in GCC 12 and `-Wdangling-reference` in GCC 13.

### The tools and their flags

1. Clang `[[clang::lifetimebound]]` annotates a parameter whose lifetime the return value borrows. The 23.1.0 suggestion diagnostic names it: `parameter in intra-TU function should be marked [[clang::lifetimebound]]`. The attribute is documented in the Clang attribute reference (not re-run on 2026-11-06).
2. Clang `-Wlifetime-safety` is a CFG-based intra-procedural analysis (23.1.0 release notes). It is off by default and enabled by `-Weverything`; `-Wno-lifetime-safety` or `-fno-lifetime-safety` turns it off. Related flags that I ran and that compiled: `-Wlifetime-safety-suggestions`, `-Wlifetime-safety-noescape` and `-Wlifetime-safety-dangling-field`.
3. Clang's capture attribute has new spellings in 23.1: `lifetime_capture_by_this`, `lifetime_capture_by_global` and `lifetime_capture_by_unknown`. Passing `this`, `global` or `unknown` as an argument is deprecated and goes in the next release.
4. MSVC's lifetime checks are C26815 and C26816 in the C++ Core Check. User types need `[[msvc::lifetimebound]]`, available since MSVC 17.7. They do not read the Clang attribute.
5. `gsl::not_null<T*>` from Microsoft GSL or a hand-rolled equivalent encodes non-null at the type level. It does not address lifetime (not re-run on 2026-11-06).
6. `std::experimental::scope_exit` from Library Fundamentals (P0052) runs a cleanup on every scope exit. libstdc++ ships it in `<experimental/scope>`.

The earlier version of this page said `std::scope_exit` was "ratified into C++26". It is not. The C++26 draft's header list has no scope header (eel.is/c++draft/headers, read 2026-11-06), and `#include <scope>` fails on GCC 16.2 with `fatal error: scope: No such file or directory`. The experimental header `<experimental/scope>` compiled and ran.

The earlier text also said P1179 is implemented as `lifetime_capture_by`. P1179 is Sutter's lifetime profile proposal, and the Clang attribute is a separate feature.

### The trunk rename

On Clang trunk, `-Wlifetime-safety-invalidation` is now `-Wlifetime-safety-experimental-invalidation`. Commit `8e635b365d` of 2026-10-20 in llvm-project made the change. It also added an experimental group that is not part of `-Wlifetime-safety-all`. The commit message says the checking "can produce false positives or even non-actionable warnings".

On Compiler Explorer, Clang 23.1.0 warned `local variable 'v' is later invalidated [-Wlifetime-safety-invalidation]` for `int& r = v[0]; v.push_back(4); return r;`. On trunk the old name was `unknown warning option` and the new name produced the same warning. I read the rename in the in-progress release notes and the commit. I did not find a 23.1.x release-notes page that mentions it.

### CMake recipe

```cmake
if(CMAKE_CXX_COMPILER_ID MATCHES "Clang")
    add_compile_options(
        -Wlifetime-safety             # Clang 23.1+; older Clang warns "unknown warning option"
        -Wlifetime-safety-suggestions
    )
elseif(CMAKE_CXX_COMPILER_ID STREQUAL "GNU")
    add_compile_options(
        -Wdangling-reference          # GCC 13+
        -Wdangling-pointer            # GCC 12+
    )
elseif(CMAKE_CXX_COMPILER_ID STREQUAL "MSVC")
    add_compile_options(/analyze /analyze:plugin EspXEngine.dll)   # C++ Core Check
endif()
```

I ran each of these flags by hand on Compiler Explorer and did not run the fragment through CMake (not re-run on 2026-11-06). Add per-target overrides where a translation unit has known false positives.

## Reflection today

The sample above shows the gap: no tool flagged `moved_frame`. A consteval predicate cannot find that bug, but it can force every non-owning view member to declare its borrow intent. It walks `T`'s data members and refuses to compile when a view (`std::string_view`, `std::span`, a reference or a raw pointer) lacks a P3394 `[[=borrows_from{}]]` annotation. The annotation has no runtime effect.

```cpp
struct borrows_from {};   // P3394 tag; empty (must be a structural type)

template <typename T>
consteval bool meets_borrow_annotated() {
    constexpr auto ctx = std::meta::access_context::unchecked();
    template for (constexpr auto m
                  : std::define_static_array(
                      std::meta::nonstatic_data_members_of(^^T, ctx))) {
        using FieldT = [:std::meta::type_of(m):];
        if constexpr (needs_borrow_annotation<FieldT>) {
            static_assert(has_annotation<borrows_from>(m),
                "lifetime-safety: non-owning view member needs a "
                "[[=borrows_from{}]] annotation. Without it, a move "
                "of the enclosing struct can dangle the view with no "
                "compiler diagnostic.");
        }
    }
    return true;
}

// OK: every view member is annotated.
struct ParsedFrame {
    std::string                                  payload;
    [[=borrows_from{}]] std::string_view header;
    [[=borrows_from{}]] std::string_view body;
};
```

```
lifetime-safety check passed for ParsedFrame.
```

The page used to say this runs on GCC 16.1 as well. On GCC 16.2 (`-std=c++26 -freflection`, with `<meta>` in place of `<experimental/meta>`) the stored source fails: the check reports `ParsedFrame`'s annotated members as unannotated. Changing the comparison in `has_annotation` from `std::meta::type_of(a) == ^^Tag` to `std::meta::remove_const(std::meta::type_of(a)) == ^^Tag` makes it pass (exit 0, same output). I did not change the example repository. The container image the page used to cite was pruned, so the `docker run` line is gone.

### The empty tag

The example source says a payload such as `borrows_from{"payload"}` is not possible, because P3394 annotation values must be structural types and `string_view` is not one. I did not test a payload variant. The empty tag still forces the author to write a marker, so a `string_view` member without `[[=borrows_from{}]]` is a visible omission in review. It checks that the intent is written down. It does not check that the intent is true.

The same walker pattern composes with the [hardened-stdlib schema lint](/toolset/hardened-stdlib/), which forbids raw pointers and C arrays, and with the [qualified-compilers MISRA Rule 11.0.1 lint](/toolset/qualified-compilers/), which wants private members. Add a predicate and the schema enforces it. Remove one and the build keeps working.

The <PostLink slug="reflection-dangling-signature">2 November post</PostLink> uses reflection differently, to lint function signatures that return a view of a by-value owner.

## Where this is heading

Profiles ([P3081R2](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2025/p3081r2.pdf) by Sutter, [P3589R1](https://isocpp.org/files/papers/P3589R1.pdf) by Dos Reis, [P3984R0](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/p3984r0.pdf) by Stroustrup) would move lifetime checks from warnings to a language-level subset. They are papers. <PostLink slug="profiles-p4415-implementation-status">The 31 October post</PostLink> covers the two experimental implementations that P4415R0 reports; I did not re-run them on 2026-11-06.

Token injection (P3294) is the other idea. Compiler Explorer lists no P3294 build on 2026-11-06, and the sketch below is pseudo-code that no compiler accepts:

```cpp
// pseudo-code, not C++ any compiler accepts today
[[ inject(borrow_safe_accessors) ]]
struct ParsedFrame {
    std::string payload;
    [[=borrows_from{}]] std::string_view header;
    [[=borrows_from{}]] std::string_view body;
};
// would inject: std::expected<std::string_view, dangle_error> view_header() const
// would inject: a move constructor that re-points the views at the new payload
```
