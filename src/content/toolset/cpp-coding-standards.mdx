A regulated C++ project picks a coding standard. MISRA C++:2023 is common in automotive, SEI CERT C++ in defensive-coding programmes, and the JSF AV C++ rules in older avionics. Then someone asks for a second standard, and two analyzer passes with two suppression lists appear. This page compares the three, says what clang-tidy provides, and shows a reflection pattern that composes structural rules in one `static_assert`.

## In short

- clang-tidy 23.1.1 has no `misra-*` and no `autosar-*` checks, and neither does the current check list. The earlier version of this page said it did.
- JSF AV C++ Rev C is dated December 2005, not 2020. It has 221 rules.
- The demo's rule labels do not match the standards. The predicate labelled "JSF AV Rule 75" checks for bit-fields, but AV Rule 75 is about initialization-list order. The same mismatch applies to the MISRA and CERT labels, below.
- The bundle itself ran on Clang (Bloomberg fork), GCC 16.2 and GCC trunk on 2026-11-06.
- I give no rule counts for MISRA C++:2023 or SEI CERT C++. I found no primary source I could read.

## Today

### The three standards side by side

| Standard | Typical industry | Body | Format | Rules |
|---|---|---|---|---|
| MISRA C++:2023 | Automotive (ISO 26262), industrial (IEC 61508) | The MISRA Consortium | Paid PDF | not checked |
| SEI CERT C++ | Defensive coding in avionics, defense and government | Carnegie Mellon SEI | Free, web | not checked |
| JSF AV C++ | Older DO-178C avionics | Lockheed Martin / JSF program | Free PDF | 221 in Rev C (December 2005) |

The industries are the page's earlier description and I did not re-verify them. The JSF count and date come from the Rev C PDF, which numbers rules up to AV Rule 221. MISRA's [announcement](https://misra.org.uk/misra-cpp2023-released-including-hardcopy/) says MISRA C++:2023 was published in October 2023, targets C++17 and is the latest edition.

### MISRA C++:2023 and AUTOSAR C++14

In 2019 MISRA and AUTOSAR [announced](https://www.autosar.org/news-events/detail/misra-consortium-announce-integration-of-autosar-c-coding-guidelines-into-updated-industry-standard) that their C++ guidelines would be merged into one publication. Perforce describes MISRA C++:2023 as integrating the AUTOSAR C++14 guidelines. I did not find a statement that AUTOSAR C++14 is formally withdrawn. Several tool vendors still offer an "AUTOSAR C++14" rule set, so ask your vendor which edition a safety case should cite.

### Tool support today

| Tool | Coverage | Notes |
|---|---|---|
| clang-tidy | `cert-*` (43 checks, C and C++) and `cppcoreguidelines-*` (43 checks in 23.1.1) | Open source and partial. There are no `misra-*` or `autosar-*` checks in 23.1.1 or in the current documentation. |
| Commercial analyzers | PVS-Studio, Coverity, Helix QAC and Parasoft C/C++test advertise MISRA and CERT rule sets | Vendor claims from the earlier text; I did not check any of them. |

The clang-tidy counts come from `clang-tidy --checks='*' --list-checks` (23.1.1) and the [check list](https://clang.llvm.org/extra/clang-tidy/checks/list.html), read on 2026-11-06. Always verify a project's rule list against the standard's full text.

### The multi-standard problem

When one header is consumed by two projects under different standards, CI runs both analyzer passes. The rules overlap, and they disagree on edge cases. Each disagreement becomes a per-team allowlist, and allowlists drift. The section below encodes structural rules as consteval predicates over `T`'s reflection, so one `static_assert` applies a bundle.

## Reflection today

Encode each rule as a consteval predicate over `nonstatic_data_members_of(^^T)` and compose with `&&`. The sketch below shows the shape; the full source is linked after it. The comments are the embed's own rule labels, which I corrected after checking the standards (next subsection).

```cpp
namespace standards {

// Embed label "MISRA C++:2023 Rule 11.0.1": data members must be private.
template <typename T>
consteval bool meets_misra_11_0_1();

// Embed label "CERT C++ DCL56-CPP (approximation)": no raw pointer members.
template <typename T>
consteval bool meets_cert_dcl56_cpp();

// Embed label "JSF AV C++ Rule 75": no bit-field members.
template <typename T>
consteval bool meets_jsf_av_75();

template <typename T>
consteval bool all() {
    return meets_misra_11_0_1<T>()
        && meets_cert_dcl56_cpp<T>()
        && meets_jsf_av_75<T>();
}

}  // namespace standards

class SensorReading {
    double  value_;
    long    timestamp_;
    bool    valid_;
public: /* accessors */
};

static_assert(standards::all<SensorReading>());   // passes
```

### What the demo's rule labels really are

I checked the labels against the standards on 2026-11-06 and they do not hold.

- Rule 75 of JSF AV C++. In Rev C (December 2005), AV Rule 75 says members of an initialization list shall be listed in declaration order. The bit-field rule is AV Rule 154, which restricts the types of bit-fields rather than banning them.
- DCL56-CPP. SEI CERT C++ DCL56-CPP is "Avoid cycles during initialization of static objects", per the CERT wiki and tool vendors' documentation. "No raw pointer members" is not that rule, and the predicate's own comment calls it an approximation.
- MISRA "11.0.1". I could not find MISRA C++:2023 Rule 11.0.1 in any source I could read. The rule I found on access to data members is Rule 14.1.1, which asks that non-static data members be either all private or all public (Polyspace and Sonar document it). The predicate checks something stricter.

I cannot change the example source in this refresh. Read the three predicates as structural examples under invented names, not as implementations of those rules. A real bundle would take its rule text from the licensed standard.

### What the diagnostics show

Uncommenting each bad struct in the embed, GCC 16.2 and the Bloomberg Clang fork both fail the build. A public struct trips the private-members predicate with `MISRA C++:2023 Rule 11.0.1: non-POD class data members must be private.` A struct with an `int*` trips that one and the pointer predicate. A struct with two bit-fields trips the private-members predicate twice and the bit-field predicate twice. So the earlier claim that adding a field makes one named rule fire is not what happens: public members trip the first predicate every time.

The pattern composes with the [hardened-stdlib schema lint](/toolset/hardened-stdlib/), the [qualified-compilers lint](/toolset/qualified-compilers/), the [lifetime-safety borrow lint](/toolset/lifetime-safety-2026/), the [SoA layout transform](/toolset/simd-in-cpp-2026/) and the [supply-chain SBOM walker](/toolset/cpp-supply-chain-2026/). The qualified-compilers page uses the same "Rule 11.0.1" label, so it needs the same check. I did not touch it.

### When not to use the reflection bundle

The bundle suits structural rules, meaning data-member shape and type-level invariants. It cannot replace an analyzer for:

- cross-translation-unit analysis such as data-flow and taint propagation;
- statement-level rules such as no `goto`, or limits on recursion;
- style rules such as naming and indentation, which are clang-format's job;
- standards that mandate documentation comments.

The bundle complements analyzers. It catches structural rules at compile time, and the analyzer catches the rest in CI. Whether the analyzer-config matrix shrinks depends on how many of your rules are structural. I have not measured that.

## Where this is heading

Two C++29 candidates could change the picture. Neither is in a released compiler, and the sketches below are illustrations, not paper syntax. Profiles (P3589R2 framework, Stroustrup's profile papers of 22 October 2026) are not in the C++26 draft, and no paper I read defines a profile named after a coding standard:

```cpp
// Sketch only: misra_2023 and cert_cpp are invented profile names.
[[ profiles::enforce(misra_2023, cert_cpp) ]]
namespace sensor_fusion { /* ... */ }
```

Token injection ([P3294](https://wg21.link/p3294), latest revision R2 from 2024) describes code injection with token sequences. Using it to inject audit headers or traceability tags is my idea, not the paper's:

```cpp
// Sketch only: not syntax from P3294.
[[ inject(audit_header, traceability_tag) ]]
class SensorReading { /* ... */ };
```

As of 2026-11-06, the working approach is reflection-driven rules for structural checks and an analyzer for the rest.
