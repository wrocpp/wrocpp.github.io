## In short

- A `consteval` parser reads the schema file that `#embed` put into the program, and each table becomes a row struct with one member per column.
- A nullable column becomes a `std::optional` member. A query string is checked against the schema, and a hand-written struct can be checked for drift.
- Every misuse stops the build with a message that names the table and the column.
- The SQL subset is tiny: no joins, no `IS NULL`, and enums are strings.
- The two tables and one query in the demo added about half a second of compile time over the headers alone. Only GCC 16.2 was tried.

## One misspelled column, one build error

Here is a build error from GCC 16.2:

```text
error: static assertion failed: unknown column 'nme' in table 'users' (columns: id, name, email, age, active) in query "SELECT id, nme FROM users"
```

No database was running when it appeared. The compiler had read the schema file and parsed its `CREATE TABLE` statements in a `consteval` function. It then checked the query string against the result.

This post builds that. A SQL schema file becomes row structs with the columns as members. A `SELECT` is checked against them. The whole thing is a few hundred lines of ordinary C++26.

## One file in, one struct per table out

The schema is plain DDL. This is the whole of `schema.sql` in the demo:

```sql
CREATE TABLE users (
  id     INTEGER PRIMARY KEY,
  name   TEXT NOT NULL,
  email  TEXT,            -- nullable: becomes std::optional<std::string>
  age    INTEGER,
  active BOOLEAN NOT NULL
);

CREATE TABLE orders (
  id      INTEGER PRIMARY KEY,
  user_id INTEGER NOT NULL,
  total   REAL NOT NULL,
  note    TEXT
);
```

The `#embed` directive puts the bytes of that file into a `constexpr` array. <PostLink slug="embed-the-file">The earlier post</PostLink> covers it. A `consteval` function then turns the array into a description of the tables:

```cpp
namespace sqlschema::embedded {
inline constexpr unsigned char bytes[] = {
#embed "schema.sql"
};
inline constexpr schema_t db = parse(std::span<unsigned char const>{bytes}, "schema.sql");
static_assert(db.ok(), db.message());
}
using schema = ::sqlschema::of<::sqlschema::embedded::db>;
```

The `schema_t` type is structural. It holds a pointer to static arrays of tables and columns. Two functions keep the names alive: `std::define_static_string` and `std::define_static_array`. That makes the type usable as a non-type template parameter. This is how `of<db>` carries the schema into every type derived from it.

## Defining the row struct

A row type is one `define_aggregate` call, with one data member per column:

```cpp
template <schema_t S, std::size_t Table> struct row_for {
  struct type;
  consteval { define_aggregate(^^type, detail::row_specs(S, Table)); }
};
```

The member name is the column name, and the member type comes from the column type:

| SQL type | C++ member type |
|---|---|
| `INTEGER`, `BIGINT` | `int64_t` |
| `REAL` | `double` |
| `TEXT` | `std::string` |
| `BOOLEAN` | `bool` |

A nullable column is wrapped in `std::optional`. Nullable means the column is neither `NOT NULL` nor a `PRIMARY KEY`. The demo prints the generated structs, and the `email` and `age` columns come out as optionals:

```cpp
using Users = schema::row<"users">;
Users u{.id = 1, .name = "Ann", .email = std::nullopt, .age = 34, .active = true};
```

```text
struct users {
  int64_t id;
  std::string name;
  std::optional<std::string> email;
  std::optional<int64_t> age;
  bool active;
};
```

Designated initializers work on it. That is the point of the exercise: the struct is an aggregate, so the compiler checks the member names and types at every use.

## A query checked against the schema

`schema::query<"...">` takes a `SELECT` as a string template argument. It parses the query with the same small lexer and finds the table and the columns. It then defines a result struct with the selected columns in the order written. A single `WHERE column OP ?` gives the query one parameter whose type is the column's:

```cpp
using Adults = schema::query<"SELECT id, name, email FROM users WHERE age >= ? ORDER BY id">;
static_assert(std::is_same_v<Adults::params, std::tuple<std::int64_t>>);
static_assert(std::is_same_v<decltype(Adults::row::email), std::optional<std::string>>);

auto q = Adults::bind(18);   // q.args is a std::tuple<std::int64_t>, q.sql the query text
```

The `bind` function list-initializes the parameter from the argument. So 18 (an `int`) is accepted for an `int64_t`, and 18.5 is not, because that would narrow.

The parameter takes the base type of the column even when the column is nullable. In SQL a comparison with `NULL` never matches. A condition such as `age >= ?` given an optional value would therefore be a bug. The `bind` function refuses it and says so.

## What the compiler says when something is wrong

Each row is one misuse. The demo's source has a macro for each, such as `-DV_UNKNOWN_COLUMN`. The text is the first `error:` line from GCC 16.2.0 in the `gcc:16.2` Docker image, with the file position removed:

| Misuse | First error line |
|---|---|
| schema has `name VARCHAR` | `static assertion failed: schema.sql:3:8: table 'users', column 'name': expected a type (INTEGER, BIGINT, REAL, TEXT or BOOLEAN), found 'VARCHAR'` |
| a column called `class` | `static assertion failed: schema.sql:2:3: table 't', column 'class': 'class' is a C++ keyword and cannot name a struct member` |
| `schema::row<"usrs">` | `static assertion failed: unknown table 'usrs' (tables: users, orders)` |
| `SELECT id, nme FROM users` | `static assertion failed: unknown column 'nme' in table 'users' (columns: id, name, email, age, active) in query "SELECT id, nme FROM users"` |
| `... WHERE age > 18` | `static assertion failed: expected '?' after the operator on column 'age' (literals are not supported), found '1' in query "SELECT id FROM users WHERE age > 18"` |
| `bind("adult")` | `static assertion failed: parameter 1 of the query is users.age >= ?: expected int64_t, got const char* (query "...")` |
| `bind(18.5)` | `static assertion failed: parameter 1 of the query is users.age >= ?: expected int64_t, got double (query "...")` |
| `bind(std::optional<std::int64_t>{18})` | `static assertion failed: parameter 1 of the query is users.age >= ?: got std::optional<int64_t>; a comparison with NULL never matches, pass the int64_t itself (query "...")` |

The schema errors carry the position inside the `.sql` file, not inside the C++ file, because the file name is a parameter of `parse`. For the `#embed` form, GCC reports the `static_assert` itself at the header line that contains it. The message after the colon carries the DDL position.

Each of these errors is followed by a long instantiation note that spells the whole schema as a literal. A reader looks at the `error:` line, and the note grows with the number of tables.

## Why the parser rejects keywords

The keyword row has a reason. Suppose the parser handed `class` straight to `define_aggregate`. GCC would say `name is a keyword`, naming neither the table nor the column. So the parser checks first, against a list of C++ keywords, and the message can name them.

The check is deliberately stricter than the compiler. I tried the alternative tokens on GCC 16.2, and it accepts tokens such as `or` and `not` as member names. A member access like `r.or` cannot be written in source, and the library rejects them anyway.

## Checking a struct you wrote by hand

Not every struct should be generated. Some code wants its own `User` type with methods. `schema::drift<T, "users">` compares a hand-written struct with the table and returns a description of every difference, or an empty string:

```cpp
struct User { std::int64_t id; std::string name; std::optional<std::string> email;
              std::optional<std::int64_t> age; bool active; };
static_assert(schema::matches<User, "users">);
```

This compiles. Now take a `Stale` struct that has fallen behind the schema. Its `email` member is a plain `std::string`. It has no `age` member and an extra `score` member. The message looks like this:

```text
nullability: Stale::email is std::string but users.email is nullable (expected std::optional<std::string>); missing: column users.age has no member in Stale (expected std::optional<int64_t> age); extra: Stale::score (double) is not a column of users
```

The spelling of the assertion matters. A bare `static_assert(schema::matches<Stale, "users">)` stops the build with `static assertion failed` and nothing else, no names. The form that prints the text is `static_assert(schema::drift<Stale, "users">.empty(), schema::drift<Stale, "users">)`. It works because C++26 allows a constant expression as the message. The demo's `V_BARE_MATCHES` and `V_DRIFT` macros show both.

The drift check also reports wrong types and wrong member order. The order complaint appears only when nothing else is wrong, because a missing column shifts every later index.

## Compared with sqlpp23, sqlgen and sqlx

All three solve a neighbouring problem. None of them is built on P2996, so the comparison is about where the schema lives and when it is read.

- **sqlpp23** has [`sqlpp23-ddl2cpp`](https://github.com/rbock/sqlpp23/blob/main/docs/ddl2cpp.md), a script that takes one or more DDL files and writes C++ headers (or modules) with the table definitions. It is a generation step in the build, and the generated code feeds sqlpp23's query builder. This post reads the DDL in the compiler instead of in a script. Beyond that, sqlpp23 is a complete query library, with a type-checked expression builder far beyond one `WHERE column OP ?`. I did not read its generator code, only its documentation.
- **[sqlgen](https://github.com/getml/sqlgen)** goes the other way. Its README defines schemas as C++ structs and builds on reflect-cpp. It shows compile-time errors such as an unknown column, and it lists DuckDB, MySQL/MariaDB, PostgreSQL and SQLite as backends. The struct is the source of truth there, and I did not find a description of importing an existing DDL file. Here the SQL file is the source and the structs are derived.
- **sqlx** (Rust) checks `query!` against a live database at build time. Its [CLI README](https://github.com/launchbadge/sqlx/blob/main/sqlx-cli/README.md) describes `cargo sqlx prepare`. That command saves query metadata to a `.sqlx` directory that you check in. The README says that "an active database connection will no longer be needed to build your project". That is the nearest idea to this one: a derived artifact in the repository lets the build run without a database. The artifact differs: sqlx stores metadata a real database produced, and this post parses the DDL itself and trusts it.

## Where this approach falls short

Here is what this post lacks next to the others. Nothing here talks to a database during the build, so nothing confirms that the DDL means what the parser thinks. The parser understands a small subset of one dialect. All three libraries above cover far more SQL, and sqlx checks queries against the database's own semantics.

## What the subset leaves out

The parser covers a small subset:

| Area | Supported | Not supported |
|---|---|---|
| Types | `INTEGER`, `BIGINT`, `REAL`, `TEXT`, `BOOLEAN` | `INT`, `VARCHAR(n)`, dates and blobs are errors, as the error table above shows for `VARCHAR` |
| Constraints | `NOT NULL` and a column-level `PRIMARY KEY` | table-level constraints, `DEFAULT`, foreign keys, `ALTER`, `IF NOT EXISTS`, block comments |
| Queries | one table, a column list or `*`, one optional `WHERE column OP ?` with `= < > <= >= <>`, and an optional `ORDER BY column` with `ASC` or `DESC` | joins, `IS NULL`, literals in the condition, aggregates, and any check of `INSERT` or `UPDATE` beyond the struct-matches-table check |

Here `PRIMARY KEY` implies not-null, which is true in SQLite only for rowid tables. Three more limits:

- Enums: a column that holds one of a few values is a `TEXT` column and a `std::string` member. C++26 has no `define_enum`, so the generated type cannot be an enumeration.
- Names: a column named like a C++ keyword (`class`, `default`) is a build error with no renaming syntax to get around it. I did not build a mapping such as `COLUMN class AS class_`.
- Case: SQL names match case-insensitively and members keep the spelling in the DDL. Two columns that differ only in case are rejected as duplicates.

## Compile time

I measured the string-literal demo in the `gcc:16.2` image with `-c -O0`, in three runs. It took 1.5 to 2.1 s of CPU time (user plus system). A file with an empty `main` that includes only the same standard headers (`<meta>` among them) took 0.9 to 1.0 s. So the two tables and one query in the demo cost about half a second on top of the headers. That is one schema, one query and one Docker VM. It is a single data point and says nothing about scaling.

An earlier run of a larger version used Homebrew GCC 16.2.0 on an Apple machine. It put a 50-column table at 0.78 to 0.81 s and a 200-column table at 1.76 to 1.80 s.

A first version of the parser hit the default `-fconstexpr-ops-limit` at 200 columns, because it computed a line and column for every column. Computing the position only when an error is built fixed it. Those runs are not published anywhere I can link, so treat them as unverified here.

In either measurement, each translation unit that includes the header parses the schema again. Nothing is shared between them.

## What this has not been tested on

- GCC 16.2 only: the `gcc:16.2` Docker image (aarch64 Linux) and Compiler Explorer's g162 (x86-64). I did not try clang-p2996. The call `substitute(^^std::optional, ...)` is untested there. So are `dealias` and `define_static_array` over structs. I also did not try GCC trunk or another 16.x.
- Not across translation units. The schema description holds pointers into static storage that belongs to one translation unit, so `of<db>` in two TUs gives two distinct types. I did not build that with `-flto -Wodr` and I do not know whether it is a problem for a program that passes rows between them.
- `#embed` path rules on Linux and other platforms beyond what the Docker run exercised, and no `-O2` timings.
## What was never run against a real system

- No database was involved in these demos. In an earlier version I inserted and fetched rows through SQLite's C API using the generated structs. It worked, but that code is not in the examples repository, and I am not claiming it here. Compiler Explorer has no `sqlite3.h` in any case.
- The parser was written against my own schema and my own error cases. Nobody has fed it DDL from a real project, so it will refuse things that real schemas contain.
- There is no comparison with the three libraries above beyond reading their documentation. I read the sqlpp23 and sqlx pages and the sqlgen README on 6 October 2026. I did not build or run any of them.
