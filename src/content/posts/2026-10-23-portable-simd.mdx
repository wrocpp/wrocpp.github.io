Writing SIMD by hand means picking a side. Intrinsics like `_mm256_add_ps` are precise and fast and tie the code to one instruction set, so a NEON port becomes a parallel implementation plus an `#ifdef` maze. The alternative, writing plain loops and hoping the auto-vectorizer cooperates, works until it silently stops working, usually because of a pointer alias the compiler cannot rule out.

C++26 standardises the middle path: **`<simd>`**, a portable vector type where the element type and the width are part of the type, and the ordinary arithmetic operators do the work.

```cpp
std::simd<float> a = 1.5f;
std::simd<float> b = 2.0f;
auto c = a * b;      // one instruction, whatever the target supports
```

The library chooses a native width for the target, so the same source compiles to SSE, AVX-512, or NEON. No intrinsics, no `#ifdef` per architecture, and the vectorization is explicit rather than a hopeful side effect of `-O3`.

## What runs today

GCC 16.1's libstdc++ does not yet provide the standard `<simd>` header (`__cpp_lib_simd` is undefined there). What it does provide is the Parallelism TS version the standard type grew out of, which is the same programming model under a different name:

```
width = 4
3 3 3 3
```

Four floats per vector on Compiler Explorer's baseline x86-64 target, one multiply, four results. Compile the same code with `-march=x86-64-v3` and the width becomes 8; on an ARM machine it becomes NEON. The width is a property of the target, which is exactly the point: you write the operation, the library picks the register.

Migrating later is mostly renaming. `std::experimental::native_simd<float>` becomes `std::simd<float>`, and the operator set, `simd_mask` for lane-wise conditionals, and the load and store helpers all carry over.

## When it is the right tool

`<simd>` is for data-parallel arithmetic where you already know the loop vectorizes in principle: pixel and audio buffers, physics steps, distance and dot-product kernels, anything shaped like "apply this to every element". Writing it as a `simd` type makes the vectorization *guaranteed and visible* rather than dependent on the optimizer's mood, and it is far easier to read six months later than a page of intrinsics.

It is not a replacement for the auto-vectorizer on ordinary loops, and it will not rescue code whose real problem is memory bandwidth or a dependency chain. For that last case, [the assembly and llvm-mca](/posts/verification-asm-llvm-mca/) will tell you before you rewrite anything.
