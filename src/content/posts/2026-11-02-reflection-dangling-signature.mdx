Klaus Iglberger's [first article on C++ safety](https://www.modernescpp.com/index.php/cpp-and-memory-safety-part-1/), published on 2026-10-18, asks how you can know that a piece of code is safe by reading it. A function signature can answer part of that. On GCC 16.2, a reflection lint of under 60 lines flags 3 of 5 declarations in a namespace. For one of the bugs it finds, GCC's own warnings say nothing.

## In short

- Two of the flagged declarations return a view of a by-value owner. The third returns a `const` reference that can bind a temporary argument.
- For the view case, GCC 16.2 gives no warning with `-Wall -Wextra`, and none with `-Wdangling-pointer=2`.
- The same bug prints garbage in a plain run and fails AddressSanitizer with a heap use after free.
- The lint reads signatures only. It reports a risk and proves nothing about the function body.

## Five declarations

The lint walks every function in a namespace. It runs on GCC 16.2 and on GCC trunk with `-std=c++26 -freflection`, with the same output on both:

```cpp
namespace api {
std::string_view first_word(std::string s);                             // a view of a by-value owner
std::span<const int> head(std::vector<int> v);                          // a span of a by-value owner
const std::string& longer(const std::string& a, const std::string& b);  // the std::max shape
std::string_view first_word_ok(std::string_view s);                     // a view of a view
std::string longer_ok(const std::string& a, const std::string& b);      // returns by value
}
```

## What the compiler and the sanitizer say

The next table runs the same two bugs, written out as programs, through three tools on GCC 16.2.

| Bug | `-Wall -Wextra` | Plain run | AddressSanitizer |
|---|---|---|---|
| A view returned from a by-value `std::string` | no warning | the view no longer equals its source | heap use after free |
| `longer` called with two temporaries | a `-Wdangling-reference` warning at the call | prints the length 50 | stack use after scope |

## How the lint works

The lint takes two facts from reflection. The first is the return type of each function. The second is the type of each parameter, and whether it is a reference. A view is a string view or a span. An owner is a string or a vector:

```cpp
consteval std::meta::info canon(std::meta::info t) {
  return std::meta::dealias(std::meta::remove_cvref(t));
}
consteval bool is_owner(std::meta::info t) {
  auto c = canon(t);
  return c == std::meta::dealias(^^std::string) ||
         (std::meta::has_template_arguments(c) && std::meta::template_of(c) == ^^std::vector);
}
```

My first version missed `first_word`. The expression for `std::string` names an alias, and comparing an alias with a type compares two different things. The alias needs `dealias` on both sides.

## Limits

- A signature cannot show what the body does. A function that takes a `std::string` by value and returns a view of a static string is safe, and the lint flags it.
- The lint knows two owner types and two view types. A project would list its own.
- Views stored as data members are a different check. The toolset pages on [lifetime safety](/toolset/lifetime-safety-2026/) and [memory safety](/toolset/memory-safety-cpp26-and-beyond/) show that one on the clang-p2996 fork.
- I did not test `[[clang::lifetimebound]]`, function bodies or other translation units.
