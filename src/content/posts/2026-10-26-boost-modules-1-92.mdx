In June the [state of modules](/posts/modules-2026) here came down to one sentence: `import std;` works, and `import boost;` is coming. Boost 1.92.0, released on 12 August, is the first instalment of the second half.

Six libraries gained C++20 module support: Conversion, DLL, LexicalCast, PFR, Stacktrace and TypeIndex. Out of roughly 180 Boost libraries, that is a rounding error. The mechanism they chose is what makes it worth writing about.

## You do not have to rewrite anything

The obvious way to add module support is to publish a module and let users migrate to it. Every `#include <boost/type_index.hpp>` becomes `import boost.type_index;`, across every file, all at once, and you find out afterwards whether your build got faster.

Boost did something less disruptive. Build with the CMake option:

```
-DBOOST_USE_MODULES=1
```

and then, per the TypeIndex documentation, all the `boost/type_index/...` includes implicitly do `import boost.type_index;`. Your source keeps saying `#include`. The header notices the macro and forwards to the module.

You can still write the import by hand if you want it:

```cpp
import boost.type_index;
```

and there is a path for people not using CMake, precompiling the `.cppm` directly:

```
clang++ -I ../include -std=c++20 --precompile -x c++-module boost_type_index.cppm
```

The include-forwarding trick is the part worth stealing. Modules have a genuine adoption problem that has nothing to do with whether they work: a large codebase cannot flip from includes to imports incrementally without ending up in a half-migrated state where both spellings are live and the build system has to cope with each. Making the macro do the switch turns that from a source migration into a build-flag experiment. Turn it on, measure, turn it off if it disappoints.

## What the documentation is careful to say

Boost is not overselling this. The TypeIndex module page says support is at an early stage and that targets, flags and behaviour may change. It also notes that for the best compile times you want `import std;` available when building the module, which quietly restates the dependency that has held modules back everywhere else: the payoff arrives when the whole chain is modularised, not when one link is.

Stacktrace and TypeIndex are both tested with and without `import std;`, which suggests the maintainers expect a long stretch where neither assumption is safe.

## Where this leaves the build

Nowhere dramatic yet, and it would be dishonest to pretend otherwise. Six libraries, an early-stage flag, and an explicit warning that the interface may move. Nobody should be rewriting a build on this.

What changed is the shape of the problem. A year ago the honest answer about Boost and modules was that the work had not started in a form you could try. Now there is a flag, a documented module name, and a migration story that does not require touching source. The next question is whether the remaining libraries follow the same pattern, because six libraries each inventing their own module naming and their own opt-in macro would be considerably worse than none.

One caveat about evidence. Compiler Explorer does not yet carry Boost 1.92 (its newest is 1.90.0), so there is no clickable demonstration to attach here. Everything above is from the release notes and the library documentation rather than from a build I ran. When CE catches up, a working `import boost.type_index;` is worth a follow-up.

## What else is in 1.92

Modules are the headline but not the release. Nothing new joined the collection this
time, and the changes that matter are inside libraries people already depend on.

Container gained a `hub` container, and unchecked variants of `emplace_back` and
`push_back` for vectors that skip the capacity test when you have already
guaranteed it. Lockfree gained two queues, `mpsc_weak_queue` and
`bounded_ticket_queue`. Asio picked up scheduler configuration parameters and
`io_uring` tuning knobs. Unordered learned C++20 ranges, so `insert_range` and
construction from a range now work. Graph added Louvain community detection and
dropped its dependency on Boost.StaticAssert.

Two deprecations are worth diarising. Filesystem's templated `initial_path()`
overloads are deprecated and go away in v4. More consequentially, 1.92 is the last
release in which Heap and Lockfree support C++14; both require C++17 from the next
one. That is narrower than the C++14 sunset it is sometimes reported as, since it
binds those two libraries rather than Boost as a whole, but if you are pinned to
C++14 and use either, this release is your ceiling.

The `hub` container deserves its own piece rather than a paragraph here, and it is
blocked on the same missing Compiler Explorer version as everything else above.
