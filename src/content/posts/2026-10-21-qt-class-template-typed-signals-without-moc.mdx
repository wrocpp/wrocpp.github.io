## In short

- A reader read the README of reflect-moc and named its remaining limit, a class template with signals, as exactly his case.
- The cause was one line: a template specialization has no identifier, and the code that names a class asked for one.
- One container template now declares typed signals, and one generic model serves seven Qt containers, from `QList` to `QSet`.
- 224,000 random steps are checked against a plain reference, and six deliberately wrong adapters are all caught.
- Against a rebuilt `QVariant` version, the typed one is faster per emit (26 against 38 ns) and per change for a list. Removal from a hash model is the exception, and the typed one costs 112 bytes per container against 24.
- I have not seen his code. The tests come from the Qt model contract, and `QMultiMap` is not supported.

## What he asked for

Leonardo Rossi described the problem in [a LinkedIn post](https://lnkd.in/p/ePDiicun) after <PostLink slug="qt-four-examples-without-moc">the post on four Qt examples</PostLink>. His team needed observable containers (lists, maps, tables) for many data types, so they had to be templates. moc rejects `Q_OBJECT` in a class template. So they split each one:

- a small non-template `QObject` declares the signals, with one `QVariant` key type for every container
- a typed template inherits it and does the work, without `Q_OBJECT`
- a plain class built on the template adds `Q_OBJECT` again and signals of its own

He listed what that cost. The key travels as a `QVariant`. The wiring between data and views had been copied by hand into 19 files, with ghost rows and ghost selections. He also wrote that a class template with signals is still on reflect-moc's list of limits, which is his case.

## Why the template failed

On the commit before the fix, a template with `RQT_OBJECT` and signals did not build:

```text
uncaught exception of type 'std::meta::exception';
'what()': 'reflection with has_identifier false'
```

The function that builds the class name called `identifier_of` on the class. A specialization such as `ObservableContainer<QHash<unsigned, Sample>>` has no identifier, so reflection threw. Nothing else needed a change: the anchor member, the signal offsets and the meta-object all work on a specialization. The fix names a type without an identifier by the compiler's own spelling ([`tables.hpp`](https://github.com/wrocpp/reflect-moc/blob/df5836e1613a1ca8d8dcf93a72b05fca4d3e832b/include/reflect_moc/qt/tables.hpp)).

## Typed signals in one class

The key type comes from the container: the hash key for a `QHash`, the index for a `QList`. The signals carry it as it is:

```cpp
template <class C>
class ObservableContainer : public QObject {
  RQT_OBJECT

 public:
  using Key = typename ContainerTraits<C>::Key;
  using Value = typename ContainerTraits<C>::Value;

  bool insert(const Key& key, Value value = Value{});
  bool remove(const Key& key);
  bool replace(const Key& key, Value value);
  bool move(const Key& from, const Key& to);  // a list only
  bool clear();

 signals:
  rqt::signal<void(const Key&)> entryAboutToBeAdded;
  rqt::signal<void(const Key&)> entryAdded;
  // the same pair for removed and changed; a pair for moved and for cleared
};
```

A mutator that is asked for something invalid returns `false`, changes nothing and emits nothing. That covers an index out of range, a key already present and a replace of a missing key. So a bad call cannot leave a view out of step with the container. The `QVariant` is gone from the signals, and so is the signals-only base class.

## One model for every container

A model has to pair every begin call with its end call and find the right row. `ContainerModel<C>` does that once, from the container's signals. A new data type needs a formatter and nothing else. The row comes from a different place for each kind of container:

| container | row order | where the row comes from |
|---|---|---|
| `QList`, `QQueue`, `QStack`, `QStringList` | the index | the key is the row |
| `QMap` | the key order | counted from the key at announcement time |
| `QHash`, `QSet` | the order of insertion | a key list the model keeps |

The map row is counted at announcement time because a removed key is already gone when the removal is confirmed. The code is in [`examples/qt/observable_models`](https://github.com/wrocpp/reflect-moc/tree/9e1f42da938afb454fcba0abe1758adbe771ea7f/examples/qt/observable_models), with a smaller [`observable_container`](https://github.com/wrocpp/reflect-moc/tree/9e1f42da938afb454fcba0abe1758adbe771ea7f/examples/qt/observable_container) that keeps his split next to the one-class version. Both builds print the same 9 lines under `QAbstractItemModelTester`, and the one-class build has no warnings and runs no moc.

## How ghost rows are caught

A ghost row is a row that a view shows and the model no longer has. A view learns about changes only from signals. So the test keeps a mirror of what a view would believe, built from signals alone. After every step it compares the mirror with the live model.

Each step applies one random change to both the container and a plain reference. It picks from insert, remove, replace, move, clear and select. Afterwards the container, model, mirror, selection and a persistent index must all agree with the reference. `QAbstractItemModelTester` runs in fatal mode. There are 8 seeds of 4,000 steps for each of 7 containers. That is 224,000 steps, about 192,000 of them change requests and the rest row selections. The run takes 1.5 seconds.

To check that the test can fail, I wrote six adapters with one mistake each. All six are reported, and the right adapter is not:

| mistake | what reports it |
|---|---|
| no end call after an insert, a move or a reset | the change was announced and never confirmed |
| the insert announced after the container changed | the row count is not what the change implies |
| the removal announced for the wrong row | the mirror differs from the model |
| a value replaced with no `dataChanged` | the mirror differs from the model |

The last two are the instructive ones. Only the mirror caught them. The model reads the container live, so a check built from the model's own data agrees with it and sees nothing wrong.

I also ran 31 hand-listed mutants on the headers, because Mull needs clang and the image has only GCC. The first run killed 24 and exposed two gaps. Nothing tested the container's own announcements, and nothing checked that a list model has no rows under a row. Both are closed. The final count is 30 killed and 1 survivor, which is equivalent: `upperBound` for `lowerBound` on a key that is not in the map yet.

## Naming a specialization

Qt reports a class name for every meta-object. For a specialization, reflect-moc uses the compiler's spelling. On GCC 16.2 that is `ObservableContainer<QHash<unsigned int, Sample> >`, with the space before the last bracket. The text is implementation-defined, so a test that pins it is pinned to one compiler.

The demo below has no Qt. It prints `has_identifier` for two specializations of a template and lists the typed signal members of each.

For a stable name, set one with `RQT_CLASS_NAME(NameOf<T>::value)` in the class, or `[[=rqt::class_name{"SampleContainer"}]]` on a plain class. One difference from moc shows in the signatures: a `qsizetype` argument is registered as `qlonglong`, in a template and in a plain class.

## What it costs against the QVariant version

His post says the `QVariant` design is not the fastest, so I measured it. The twin is [a reconstruction from his description](https://github.com/wrocpp/reflect-moc/tree/0137abfdb2645cdc4eb753f2dbe7a4946df1e522/examples/qt/observable_models_qvariant). It has a non-template base with `Q_OBJECT` and ten signals keyed by `QVariant`. A template container boxes the key and a model unboxes it. Its row logic is copied from the typed model, so only the way the key travels differs. It passes the same random test as the typed version before anything is timed, and a copy with one wrong row fails that test.

| per change, 1,000 entries (median of 7, ns) | QVariant | typed |
|---|---|---|
| `QList` replace | 91.5 | 72.4 |
| `QHash` fill | 162.4 | 120.5 |
| `QMap` replace | 1,857.9 | 1,875.6 |
| `QHash` drain, x86_64 (not Mac) | 267.5 | 297.8 |
| one emit, `quint32` key | 37.8 | 25.8 |
| one emit, 32-byte key | 46.0 | 28.2 |
| bytes per container (ten signals, a `QHash`) | 24 | 112 |
| compile, one translation unit (s) | 5.5 + 3.5 for moc | 7.9 |

On the Mac the typed version is as fast or faster in all ten rows of the full table. It is 15 to 25 percent faster for a list and a hash. A map shows no difference, because finding the row dominates both. A `quint32` key already shows the gap on a bare emit, so it is not only the heap allocation that a large key causes.

I also ran it on a GitHub x86_64 runner, where the spread is under 2 percent. The picture is the same, with one result that goes against the typed version. Removing entries from a hash model is slower: 1.11 times at 1,000 entries and 1.73 times at 100,000. I do not know why. The model code on that path is identical in the two builds, and only the signal transport differs.

### What it costs in memory and compile time

Each data-member signal takes 8 bytes in every instance, so a container with ten signals is 112 bytes against 24. `RQT_OBJECT_STATIC` with `rqt::static_signal` brings it back to 24 bytes. The reflection translation unit compiles 2.4 seconds slower on the Mac, and 1.1 seconds faster once moc and its generated file are counted. On x86_64 it is 2.1 seconds slower and 0.4 seconds faster. Which side wins there depends on how many files include the header.

### How far to trust it

These numbers come from one script ([`run.sh`](https://github.com/wrocpp/reflect-moc/blob/0137abfdb2645cdc4eb753f2dbe7a4946df1e522/tests/qt/measure/observable_bench/run.sh)) The Mac was in use, so treat differences under about 10 percent there as noise. The x86_64 run is the manual [`bench` workflow](https://github.com/wrocpp/reflect-moc/actions/runs/39480417966). The full tables, the spread of every cell and how to repeat it are in [`docs/measurements.md`](https://github.com/wrocpp/reflect-moc/blob/0137abfdb2645cdc4eb753f2dbe7a4946df1e522/docs/measurements.md).

## What this does not show

- The library is GCC only, tested on 16.2 and Qt 6.10 (Docker on aarch64, and [CI on x86_64](https://github.com/wrocpp/reflect-moc/actions/runs/39465952513)). Nothing here ran on clang or MSVC.
- I have only the description in his post. The tests come from the `QAbstractItemModel` contract, so they show that these classes keep it. They do not show that his application has no ghost rows.
- `QMultiMap` and `QMultiHash` are not supported. Two entries can share a key there, so a key does not identify an entry.
- Proxy models, views that cache row data, and QML registration of a specialization are not covered.
- The same specialization in two translation units is not tested. The library does that for plain classes, and I did not write the template version.
- The map and hash models cost linear time. Finding a row from a key, or a key from a row, walks the container or the model's key list. A replace takes about 28 microseconds in a hash model of 100,000 entries and about 54 in a map of 10,000. The `QVariant` twin costs the same, since the row logic is shared. I have not added an index.
- If a container's own insert throws after the "about" signal, the model is left mid-change, as a hand-written adapter would be.
- The model is a single-column list model with display and key roles. It has no editing, no tables or trees and no range inserts, and it assumes the container and the model live in one thread.
- The speed numbers come from GCC 16.2 on two machines, with no view attached and with my reconstruction of his design. A real application with a view would see smaller differences, and his code could differ from my twin.
- `tools/rqt-migrate` cannot port this shape. It reads `moc --output-json`, and moc cannot read a template, so the reflect-moc tree here is written by hand. A step that folds a signals-only base into the template does not exist yet.
