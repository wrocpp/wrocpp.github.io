## In short

- A test runner can find tests by reflection in one namespace, but `members_of` sees only the declarations of its own translation unit.
- Tests in other files need one registrar line per file, and that line needs a unique lambda argument. Without the lambda, the build links, reports 7 passes and runs the wrong tests.
- Neither the compiler, the linker nor `-Wodr` under LTO reports the mistake. A static library also drops the registrars unless the linker takes the whole archive.
- The same machinery registers a type with EnTT in one line, in place of 8 to 53 lines of hand-written registration.
- Everything here was run on GCC 16.2 only.

## A green run that skipped tests

This is the output of a test runner that discovers its tests by reflection. It is linked from two source files that each declare some tests in `namespace tests`:

```text
registry (fed by static initialisation): 7 case(s)
pass   adds
pass   adds
pass   in_runner
pass   parses[n=3]
pass   parses[n=3]
pass   parses[n=4]
pass   parses[n=4]
7 cases, 0 failed
```

Every line says `pass`, and the count is right. But `adds` ran twice, and three tests from the second file never ran at all:

- `subtracts`
- `by_name`
- `known_bug`

The compiler and the linker said nothing, and neither did `-Wodr` under LTO. The difference between this build and the correct one is a `[] {}` that I left out of one line.

The rest of the post builds the working version. It is about 190 lines of non-comment C++26 in one header. The post then goes through what breaks it. A second part uses the same machinery to register a type with EnTT's runtime reflection in one line.

## Finding the tests in one translation unit

A test is a function in a namespace with an annotation on it. The annotation is a plain constant, which <PostLink slug="annotations">the annotations post</PostLink> covers:

```cpp
namespace tests {
using fixtures::Fixture;
[[=rqt::test]] void adds() { rqt::expect(1 + 1 == 2); }
[[=rqt::test]] void parses(Fixture& f /* by TYPE */, [[=rqt::param(3), =rqt::param(4)]] int n) { rqt::expect(f.base + n >= 43, "base + n"); }
[[=rqt::test]] void by_name(int seed /* by NAME */, int offset) { rqt::expect(seed == 42 && offset == 1000, "seed/offset"); }
[[=rqt::test, =rqt::xfail]] void known_bug() { rqt::expect(false, "known bug"); }
void helper_not_a_test() {}
}

int main() { return rqt::run(rqt::discover<^^tests, ^^fixtures>()) == 0 ? 0 : 1; }
```

The `discover` function runs in a `consteval` context. It calls `members_of(^^tests, access_context::unchecked())` and keeps the functions that carry `[[=rqt::test]]`. It then expands over them with `template for` and builds a call for each one. The arguments come from a second namespace, `fixtures`, which is plain code:

```cpp
namespace fixtures {
struct Fixture { int base; };
inline Fixture make_fixture() { return Fixture{40}; }   // resolved by TYPE
inline int seed() { return 42; }                        // resolved by NAME (parameter named seed)
inline int offset() { return 1000; }                    // a second int fixture: type alone is ambiguous
}
```

### Filling the parameters

A parameter is filled by the fixture function whose name equals the parameter's name and whose return type matches. If no name matches, the unique function that returns that type is used. Two examples show both rules:

- The `parses` test takes a `Fixture&`. Only `make_fixture` returns one.
- `by_name` takes two `int` parameters, so the type alone is ambiguous. The name lookup picks `seed()` and `offset()`. It reads each name with `identifier_of(parameters_of(f)[i])`.

Reading a parameter's name needs `parameters_of` and `identifier_of`, and both work on GCC 16.2. Using the parameter itself inside the body does not work, and GCC says `cannot use 'x' function parameter reflection in a splice expression`. That is why the fixture lookup happens before the call.

The annotation `[[=rqt::param(3), =rqt::param(4)]]` on a parameter gives one case per entry. The cases are named `parses[n=3]` and `parses[n=4]`. The code also implements the cartesian product over several annotated parameters, but I only ran it with one.

### A smaller finding about rtest

The rtest post on jonastoth.github.io lists two things the author wanted next:

- "collect tests in 'this' translation unit", with the remark "does not seem possible to me"
- "collect tests of a module / namespace", with "should be possible, working on it"

On GCC 16.2 a walk of one namespace works, as above. So does a recursive walk starting from `^^::` that skips `std` and a few implementation namespaces. The demo `global_walk.cpp` finds tests in all four of its test namespaces:

- the global namespace
- `one`
- `one::deep`
- `two`

## Why a runner sees only its own file

A call to `members_of(^^tests)` lists the declarations of `tests` that the current translation unit has seen. A second file that declares more functions in the same namespace is a different translation unit. Its declarations are not in the first one's list.

I checked this in a spike. One file declaring `a, b` printed `a b`. Another declaring `a, b, c` printed `a b c`. The demo shows it again. The runner's file declares one test, so `discover<^^tests, ^^fixtures>()` finds 1 case there, while the namespace has 7 across three files.

So the tests of the other files have to be handed to the runner at run time. Each file that holds tests ends with one line:

```cpp
static const rqt::registrar<^^tests, ^^fixtures> tests_of_this_tu{[] {}};
```

A `registrar` object has a constructor that walks the namespace as this translation unit sees it. It pushes the cases into `rqt::registry()`, a function-local static vector. This runs during static initialisation, before `main`. The runner reads the registry, sorts it by name and runs it. Link order does not matter, because the registry is created on first use. Linking `runner.o tu_b.o tu_a.o` instead of `tu_a.o tu_b.o runner.o` gives the same 7 cases.

## The lambda that cannot be left out

The first version of `registrar` had no lambda:

```cpp
template <std::meta::info TestNs, std::meta::info Fix>
struct registrar_naive {
    registrar_naive() {
        for (auto& c : detail::collect<TestNs, Fix, void>()) registry().push_back(std::move(c));
    }
};
```

The type `registrar_naive<^^tests, ^^fixtures>` is the same in every translation unit. Its constructor is an inline function, so the linker keeps one copy of it. But the body of that constructor depends on what `tests` contained in the file that instantiated it. Two different bodies for one inline function is an ODR violation. The standard does not require anyone to diagnose it, and nobody does. In my link order the copy from the first file won. I did not look at what decides which copy is kept.

### The fix

The fix is to make the constructor a template over a type that is unique per file. A lambda expression gives you one for free. The `registrar` object takes `[] {}` as a constructor argument. The `Tag` parameter is deduced as that file's closure type, so each file instantiates its own constructor:

```cpp
template <std::meta::info TestNs, std::meta::info Fix>
struct registrar {
    template <class Tag>
    explicit registrar(Tag) {
        for (auto& c : detail::collect<TestNs, Fix, Tag>()) registry().push_back(std::move(c));
    }
};
```

The `registrar` type has no default constructor, so forgetting the lambda is a compile error: `no matching function for call to 'rqt::registrar<^^tests, ^^fixtures>::registrar()'`. I tried the obvious alternative of defaulting the tag to `std::source_location::current()`. It gives the location of the header, not of the use site, so two files got the same value. A `__COUNTER__` or `__FILE__` macro would work, and I did not want a macro in this version.

The table is what I got from `build.sh` (below) for the three link variants:

| Build | Cases reported | What ran |
|---|---|---|
| tagged `registrar`, normal link | 7 | all 7, in sorted order |
| tagged `registrar`, `-O2 -flto -Wodr -Wlto-type-mismatch -Werror` | 7 | all 7, link prints nothing |
| `registrar_naive`, normal link | 7 | `adds` twice, `parses[n=3]` twice, `parses[n=4]` twice, `in_runner`; no `subtracts`, `by_name` or `known_bug` |
| `registrar_naive`, same LTO flags | 7 | the same wrong set, link prints nothing |

The last row is the one I would not have guessed. Link-time optimisation sees both definitions and has `-Wodr` to say something about them, and it stays quiet.

## Tests in a static library

Put the same two files in a static library and link the runner against it, and the registrars are not run:

```text
registry (fed by static initialisation): 1 case(s)
```

The runner's own test is the only one left. The runner references nothing in the library's translation units. So the linker never pulls them out of the archive, and their static objects do not exist in the program. Telling the linker to take the whole archive brings the 7 cases back.

What I ran:

- **Linux aarch64, GNU ld 2.44** (the `gcc:16.2` Docker image): `-Wl,--whole-archive libtests.a -Wl,--no-whole-archive` gives 7, a plain link gives 1.
- **macOS arm64, ld64**, in the earlier spike run: `-Wl,-force_load,libtests.a` gives 7, a plain link gives 1.

What I did not run: x86-64 Linux, lld, gold, mold, or MSVC. A reader on one of those should treat the same behaviour as a guess, not a result. Shared libraries and `dlopen` I did not try at all.

## Registering a type with entt::meta

The second part is about registration of a different kind. EnTT's runtime reflection is built from a `meta_factory` chain that you write per type. This is the demo's `Player` registered by hand. It follows how the EnTT [meta documentation](https://github.com/skypjack/entt/blob/e0f4c3763967db04f116863a0ec5e35110808a26/docs/md/meta.md) builds up the API:

```cpp
struct Player {
    int hp{};
    float x{};
    float y{};
    std::string name;
    void heal(int n) { hp += n; }
};

entt::meta_factory<Player>{ctx}
    .type("Player")
    .data<&Player::hp>("hp")
    .data<&Player::x>("x")
    .data<&Player::y>("y")
    .data<&Player::name>("name")
    .func<&Player::heal>("heal");
```

and this is the reflected version:

```cpp
rqt::register_type<Player>(ctx);
```

The `register_type` helper is 41 non-comment lines in `rqt_entt.hpp`, written once. It does four things:

- It makes the factory with the type's identifier as the name.
- It adds `base<B>()` for each entry of `bases_of`.
- It adds `data<&[:m:]>(name)` for each non-static data member.
- It adds `func<&[:m:]>(name)` for each member function that is not a special member and not static.

The demo registers `Player` both ways, in two separate contexts of type `entt::meta_ctx`. It compares the results with one `operator==`. Both registrations give:

- the same type name and id (477166624)
- the same four data members and one function, in the same order
- the same results from the set and get calls and from `invoke("heal", 8)`

```text
hand : Player id=477166624 data=4 [hp,x,y,name,] func=1 [heal,] hp 42 -> 50 name=bob
refl : Player id=477166624 data=4 [hp,x,y,name,] func=1 [heal,] hp 42 -> 50 name=bob
A: hand == reflected
```

### Lines of registration

The number that sells this is the line count. I generated both forms for a struct with N members and one function, one call per line:

| Members | Hand-written (factory, `.type`, N `.data`, one `.func`) | Reflected |
|---|---|---|
| 5 | 8 lines | 1 line |
| 20 | 23 lines | 1 line |
| 50 | 53 lines | 1 line |

With 41 lines for the helper, the break-even is around six types of five members, two of twenty, or one of forty or more. That is lines of registration only. It says nothing about whether the registered members are the ones you wanted. Reflection registers every public data member and every non-special, non-static member function under its C++ name. There is no way to leave one out or rename it. An annotation that opts out would be the obvious next step, and I did not build it.

### What the helper handles

This is what the helper handled and did not, on GCC 16.2 with EnTT 4:

- Overloads work, for example `int f(int)` and `int f(int, int)`. The splice `&[:m:]` names each one, and EnTT chains them under one id. Then `invoke("f", 1)` returns 2 and `invoke("f", 1, 2)` returns 4. Const and `noexcept` members also work.
- Inheritance works through `bases_of` and `base<B>()`. A `Derived` finds the inherited data member and invokes the inherited function.
- Enums work as constants. EnTT has no enum concept, so each enumerator becomes a constant data member (`red=0 green=5 blue=6`). The splice needs parentheses, as in `data<([:e:])>`. Otherwise GCC says `unparenthesized splice expression cannot be used as a template argument`.
- A ref-qualified member such as `int k() &` stops the build with an error inside EnTT: `no matching function for call to 'entt::meta_function_helper<...>::get_rid_of_noexcept'`. Skipping such members with `is_lvalue_reference_qualified` would work around it, and I did not do that.
- Private members are skipped with the default `access_context::current()`. With `unchecked()` they are registered. The expression `&[:m:]` on a private member compiled on GCC 16.2 without an access error, so the check is not made at the splice. I did not try this on another compiler, so I do not know whether that is intended.

One more practical note. EnTT's own header does not pass `-Wextra -Werror` on GCC 16.2. The error is `entt.hpp:80944:24: error: missing initializer for member 'entt::internal::meta_func_node::next' [-Werror=missing-field-initializers]`. Including the header as a system header with `-isystem` removes the problem. Compiler Explorer adds libraries that way, so the demo above builds there even with `-Werror`.

## How Catch2, GoogleTest and EnTT register things

None of these needs a line per file, and none of this post is an argument that they should change.

### Catch2

The [tutorial](https://github.com/catchorg/Catch2/blob/devel/docs/tutorial.md) says of `TEST_CASE` that "The test automatically self-registers with the test runner". It adds that the user does not have to do anything more for the framework to pick the test up. In `catch_test_registry.hpp` the macro defines the test function and a uniquely named `const Catch::AutoReg` object in an unnamed namespace. That is my reading of the source. An unnamed namespace is a different entity in every translation unit, which is the property the lambda gives `registrar` here. Test names and tags are strings, and the docs say that the combination "must be unique within the Catch2 executable".
### GoogleTest

The [primer](https://github.com/google/googletest/blob/main/docs/primer.md) says "`TEST()` and `TEST_F()` implicitly register their tests with GoogleTest. So, unlike with many other C++ testing frameworks, you don't have to re-list all your defined tests in order to run them". It also says that `RUN_ALL_TESTS()` "runs all tests in your link unit". The macro defines a class per test and a static data member initialised with `MakeAndRegisterTestInfo`. For the rare case that needs registration at run time, the [advanced guide](https://github.com/google/googletest/blob/main/docs/advanced.md) describes `::testing::RegisterTest`, "to be used only when the `TEST` macros are insufficient".
### EnTT

Registration is explicit and typed, as in the hand-written listing above. That is a design choice that keeps what is exposed to the runtime reflection in the programmer's hands. The cost is the line count in the table. If you decide that every public member should be exposed, `register_type` removes the typing but not the choice.

### Where this design differs

The tools differ from this demo in how a test is found. Catch2 and GoogleTest need a macro at each test and no list anywhere. Here the test is a plain function with an attribute, the `members_of` function finds it, and the price is one registrar line per file.

A macro per test is less to maintain than a line per file. For an existing codebase the macro frameworks are the lower-effort route. Annotations and namespace reflection offer something else: the test is an ordinary function that other tools can also see. The same walk could generate a listing, a fixture graph or an RPC table.

Both frameworks also create their registration objects at namespace scope, with constructors that run during static initialisation. I would therefore expect a static library to be able to drop them in the same way. I did not test that, and none of the pages I read mention it.

## Compile time

These numbers are from Homebrew GCC 16.2.0 on an Apple machine (`-c -O0`, three runs, CPU time). Including EnTT costs about 1.4 s. A translation unit that registers a 5-, 20- or 50-member type costs 2.0 to 2.5 s. The reflected and the hand-written versions of the same type were within about 0.35 s of each other.

The test runner header alone is 0.5 s. A runner with 10 test functions took 0.7 s, and 100 test functions (about 134 cases) took 1.4 s. That run is from my spike notes and I have not published it anywhere linkable.

I repeated the 5- and 50-member registration builds in the `gcc:16.2` Docker image. The three runs of each build ranged from 2.1 to 4.1 s across both forms. They showed no pattern between reflected and hand-written, because the Docker VM was shared. I would not draw a conclusion from that run, and this post does not.

### Platforms and versions

- Not clang-p2996 and not GCC trunk. I did not try either.
- Linux x86-64 was only exercised through Compiler Explorer's g162 for the two single-file demos. The multi-file demo, the static library and the LTO results come from Linux aarch64 in Docker and macOS arm64 only. I did not run any of it on an x86-64 machine of my own, and I did not run it in CI.
- Linkers other than GNU ld 2.44 and Apple's ld64, as above. Shared libraries, `dlopen` and thread safety of the registry (registration happens at static initialisation, so it is single-threaded by construction).
- EnTT 3.x. Compiler Explorer offers versions up to 3.12.2 and trunk, and I used only 4.x. The local header is the single-header `entt.hpp` reporting version 4.0.0. It comes from the `main` branch at commit `e0f4c3763967` (2026-09-17, after the v4.0.0 release of 2026-07-23). Compiler Explorer's `trunk` reports 4.1.0 when I print the version macro, and I did not record its commit. The `build.sh` script downloads the pinned commit and checks its SHA-256.

### Missing features

- Not covered for `register_type`: templates, static members, bit-fields, and members inherited from a base that is not itself registered.
- Not covered for the test runner: more than one parameterised parameter per test, fixtures that need other fixtures, and fixture teardown. It has no filtering, no command line and no parallelism.
- Two translation units that both see the same declaration, for example a header that declares a test function included by both. The registrar would report that case twice.
- No performance comparison with Catch2 or GoogleTest, and I built neither. Everything I say about them comes from the pages and files linked above.
