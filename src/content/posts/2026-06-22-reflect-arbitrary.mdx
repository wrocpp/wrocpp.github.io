> **No published library.** [github.com/wrocpp/reflect_arbitrary](https://github.com/wrocpp/reflect_arbitrary) is a placeholder repository with a README only. This post describes a design sketch.

Property-based testing changed what "test coverage" means. Instead of checking one example at a time, you describe a *property* and let the test framework try hundreds of inputs:

```haskell
-- Haskell QuickCheck
prop :: User -> Bool
prop u = roundTrip u == u
```

To do that the framework needs an **`Arbitrary`** instance for every type in your test — a recipe for generating random values of that type. Haskell's QuickCheck auto-derives `Arbitrary` for any algebraic data type; Rust's `proptest` has `Arbitrary` derive macros; Java's jqwik reflects on classes at runtime.

C++ had two things stopping the same pattern: no reflection, and a test ecosystem (gtest, Catch2) organised around example-based tests. RapidCheck and FuzzTest bring property-based testing to C++. For a user type RapidCheck needs an `Arbitrary<T>` specialisation or `gen::` combinators: its documentation says to "add a specialization of the `Arbitrary` template struct". FuzzTest derives `Arbitrary<T>` itself for aggregate structs ("must have only public members, and no more than 80 fields") and needs explicit domains for custom constraints. Here is the RapidCheck case, where you **hand-write the generator**:

```cpp
// RapidCheck today — manual Arbitrary specialisation
namespace rc {
template <> struct Arbitrary<User> {
    static Gen<User> arbitrary() {
        return gen::build<User>(
            gen::set(&User::name,    gen::arbitrary<std::string>()),
            gen::set(&User::age,     gen::inRange(0, 150)),
            gen::set(&User::email,   gen::arbitrary<std::string>()),
            gen::set(&User::admin,   gen::arbitrary<bool>()));
    }
};
}
```

In RapidCheck every field appears twice. Rename `age`, forget to update the generator, and your tests silently stop exercising that case.

A library named `reflect_arbitrary` would collapse this:

```cpp
#include <reflect_arbitrary/arbitrary.hpp>  // sketch: there is no such header

struct User {
    std::string name;
    [[=gen::range(0, 150)]] int age;
    std::string email;
    bool admin;
};

// Zero manual setup — RapidCheck sees User as Arbitrary automatically.
rc::check([](User u) {
    return round_trip_json(u) == u;
});
```

That is the intended use: one `#include`, one struct. It is not what runs today.

## The walk

```cpp
// Sketch: integer_gen, float_gen, string_gen, range_gen, arbitrary_for_member and
// apply_to_members are not defined, and this was not built against RapidCheck.
namespace arb {

template <typename T>
rc::Gen<T> arbitrary() {
    if constexpr (std::is_same_v<T, bool>)               return rc::gen::arbitrary<bool>();
    else if constexpr (std::is_integral_v<T>)             return integer_gen<T>();
    else if constexpr (std::is_floating_point_v<T>)       return float_gen<T>();
    else if constexpr (std::is_same_v<T, std::string>)    return string_gen();
    else if constexpr (is_range<T>)                       return range_gen<T>();
    else if constexpr (std::is_aggregate_v<T>)            return struct_gen<T>();
    else                                                   static_assert(false, "no Arbitrary");
}

template <typename T>
rc::Gen<T> struct_gen() {
    constexpr auto ctx = std::meta::access_context::unchecked();
    static constexpr auto members =
        std::define_static_array(std::meta::nonstatic_data_members_of(^^T, ctx));
    return rc::gen::map(
        rc::gen::tuple(
            [&]<std::size_t... Is>(std::index_sequence<Is...>) {
                return std::make_tuple(arbitrary_for_member<members[Is]>()...);
            }(std::make_index_sequence<members.size()>{})),
        [](auto&& tup) {
            T result{};
            apply_to_members<T>(result, std::forward<decltype(tup)>(tup));
            return result;
        });
}

}  // namespace arb
```

For each non-static data member, we generate a value and assemble the struct. Annotations on the field (`[[=gen::range(0, 150)]]`) are consulted per-member to constrain the generator. Nested aggregates recurse.

## Constraints via annotations

```cpp
struct Order {
    [[=gen::non_empty{}, =gen::max_length(20)]] std::string sku;
    [[=gen::range(1, 1000)]]                    int quantity;
    [[=gen::regex("[a-z]+@[a-z]+\\.[a-z]{2,3}")]] std::string email;
    [[=gen::one_of("pending", "shipped", "cancelled")]] std::string status;
};
```

The annotation vocabulary in the sketch borrows from serde and Pydantic constraints. None of these annotations is implemented:

| Annotation | Effect |
|---|---|
| `gen::range(lo, hi)` | Integer / floating-point bounds |
| `gen::non_empty{}` | Vectors, strings, optional values must be non-empty / present |
| `gen::max_length(N)` | Cap strings, vectors |
| `gen::regex("pattern")` | Strings match a compile-time regex |
| `gen::one_of(v, v, v)` | Pick from a small enum of values |
| `gen::positive{}` | Shorthand for `range(1, MAX)` |
| `gen::probability(p)` | For `bool`: skew `true` rate |

All annotations are `constexpr` values (see [post 9](/posts/annotations/)); the walk would query them with `std::meta::annotations_of_with_type(member, ^^gen::range)` and the like.

## A round-trip property

Classic property-based test: serialise round-trips.

```cpp
struct User { std::string name; int age; bool admin; };

rc::check([](User u) {
    auto s = rjson::to_json(u);
    auto r = rjson::from_json<User>(s);
    return r.has_value() && *r == u;
});
```

RapidCheck tries ~100 generated `User`s by default. This post has no failing run to show. The embedded demo further down generates five users from a seeded PRNG and checks a property that cannot fail. This is what it prints on Compiler Explorer (clang-p2996, libc++), run on 6 October 2026:

## FuzzTest adapter

A FuzzTest adapter is another part of the sketch and does not exist. For LibFuzzer-backed continuous fuzzing ([Google FuzzTest](https://github.com/google/fuzztest)) it would look like this:

```cpp
#include <reflect_arbitrary/fuzztest.hpp>  // sketch: there is no such header

FUZZ_TEST(RoundTrip, [](User u) {
    EXPECT_EQ(rjson::from_json<User>(rjson::to_json(u)).value(), u);
}).WithDomains(arb::fuzztest_domain<User>());
```

A helper like `arb::fuzztest_domain<T>` would produce a FuzzTest `Domain<T>` from the same reflection walk.

## Comparison with other languages

| Language | Auto-derive `Arbitrary<T>` | Annotation-driven constraints |
|---|---|---|
| Haskell (QuickCheck) | Yes (via `Generic`) | Limited |
| Rust (proptest) | Yes (via `#[derive(Arbitrary)]`) | Yes |
| Java (jqwik) | Yes (runtime reflection) | Yes |
| Python (Hypothesis) | Yes (`@given(builds(MyClass))`) | Yes |
| C++ (pre-reflect) | RapidCheck: by hand per type. FuzzTest: derived for aggregates with public fields | No annotations; FuzzTest takes explicit domains |
| C++26 (the sketch in this post) | Designed, not built | Designed, not built |

The last column is the unusual one: in the design, constraint annotations on fields would be consumed by the generator builder at compile time, so the generated `Gen<T>` would not hold runtime metadata. It would be a direct composition of primitive generators. Nothing here builds that.

## Research context

Property-based testing has matured as a field, and the academic literature explicitly names C++'s lack of reflection as the barrier to better adoption. Nilesh Jagnik's 2024 paper *"Property Based And Fuzz Testing in C++"* lists reflection as the missing piece between C++ and Haskell/Rust ecosystems. `reflect_arbitrary` is a sketch of that missing piece, not an implementation of it.

## What a library could ship (not built)

None of this exists. It is the shape the sketch above points to:

- `arb::arbitrary<T>()` returns `rc::Gen<T>` for any reflectable type.
- `arb::fuzztest_domain<T>()` returns a FuzzTest `Domain<T>`.
- Annotation vocabulary: the 7 constraint annotations in the table above.
- Opt-out: `[[=gen::arbitrary_fn(&my_custom_gen)]]` to skip auto-derive for a single field.

A first version would handle aggregates, ranges, `std::optional` and enums. Variant types, recursive types with a depth bound and shrinking-aware annotations are open questions.
