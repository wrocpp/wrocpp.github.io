A pimpl that keeps its implementation in a buffer inside the object saves one heap allocation per object and per copy. The price is a number: the header must state the size and alignment of a type it only declares. For an `Impl` holding an `int` and two strings, that is 72 bytes with libstdc++ 16.2 and 56 with libc++. This post compares three ways to get it right on one class. It also measures the heap pimpl.

## In short

- A checked number. The header states the size and the .cpp checks it with `static_assert`. The C++26 message says which number to write. No tools, but one number per standard library.
- A generated number. Reflection finds every class annotated as an implementation and prints a header with its size. A stale header fails the build. It needs a two-pass build.
- `define_aggregate` in the header gives the exact layout with nothing to maintain. But the member list is then in the header, so nothing is hidden.
- On GCC 16.2 the heap pimpl, `unique_ptr` or `std::indirect`, is 8 bytes. It adds one allocation to every construction and every copy. The inline buffer costs what a plain member costs.
- My choice: the generator when the build can run one, the checked number otherwise.

## Why the header cannot compute the size

The point of a pimpl is that the header never defines `Impl`. Users include the header, and a change to `Impl` does not recompile them. The <PostLink slug="std-indirect-pimpl">std::indirect post</PostLink> shows the heap version, where the header holds a pointer and the size does not matter.

An inline buffer needs the size where `Impl` is incomplete. Neither `sizeof` nor reflection can help there, because both need the complete type. So the number has to come from somewhere else. Each approach below gets it from a different place.

The examples share one class. `Widget` keeps its `Impl` in a small template. The template, `inline_pimpl<T, Size, Align>`, is an aligned byte array plus placement new. Its members are templates, so they are compiled only in the .cpp, where `Impl` is complete.

## A number in the header, checked in the .cpp

The header states the size and alignment as constants. The .cpp checks them where `Impl` is complete:

```cpp
// widget.hpp
class Widget {
 public:
  struct Impl;
  static constexpr std::size_t kImplSize = 72;
  static constexpr std::size_t kImplAlign = 8;
  // ...
 private:
  inline_pimpl<Impl, kImplSize, kImplAlign> impl_;
};

// widget.cpp
static_assert(sizeof(Widget::Impl) == Widget::kImplSize, layout_message("kImplSize", sizeof(Widget::Impl)));
```

The second argument is new in C++26. [P2741](https://wg21.link/p2741) lets the message of a static assertion be any constant object with `data()` and `size()`. Here a small `consteval` function formats the real size into the text. With the constant set to 48, GCC 16.2 stops with:

```text
error: static assertion failed: set Widget::kImplSize to 72
```

Clang 22.1 gives the same text after its usual "due to requirement" clause. Make `size()` return the exact length. A larger value makes Clang print the unused tail of the buffer as NUL characters.

<GodboltEmbed id="5bavsvGdn" gccOnly gccLabel="GCC 16.2" title="A pimpl buffer whose size is checked, with a message that names the right number" gcc_subtitle="x86-64 GCC 16.2 · -std=c++26 -O1 · runs live" />

Then I built the same file, unchanged, with Clang trunk and libc++:

```text
error: static assertion failed due to requirement 'sizeof(Widget::Impl) == Widget::kImplSize': set Widget::kImplSize to 56
```

A `std::string` is 32 bytes in libstdc++ and 24 in libc++. The check catches it, but a library that builds on both needs the number twice. With the preprocessor banned from these examples, that means one header per library.

## A layout header written by reflection

The second approach removes the hand-written number. Each implementation class carries an annotation, a C++26 attribute that holds a value:

```cpp
namespace pimpl {
struct impl_of {};
}

namespace detail {
struct [[= pimpl::impl_of{}]] WidgetImpl {
  int id;
  std::string name;
  std::string label;
};
}
```

A small generator program includes the implementation headers. It walks the namespace with `std::meta::members_of`, keeps the types that carry the annotation, and prints their size and alignment. The generator loops over `annotations_of` and compares each annotation's type. GCC 16.2 also has `annotations_of_with_type`, but the Bloomberg Clang fork does not:

```cpp
template for (constexpr std::meta::info member : members) {
  if constexpr (std::meta::is_type(member) && is_pimpl_impl(member)) {
    std::println("inline constexpr std::size_t {}_size = {};", std::meta::identifier_of(member),
                 std::meta::size_of(member));
    // ... the same line for alignment_of
  }
}
```

For two annotated classes and one without the annotation it prints:

```text
namespace detail {
inline constexpr std::size_t WidgetImpl_size = 72;
inline constexpr std::size_t WidgetImpl_align = 8;
inline constexpr std::size_t GadgetImpl_size = 16;
inline constexpr std::size_t GadgetImpl_align = 8;
}  // namespace detail
```

<GodboltEmbed id="KE96xM5rh" gccOnly gccLabel="GCC 16.2" title="Reflection finds every annotated Impl and prints its layout" gcc_subtitle="x86-64 GCC 16.2 · -std=c++26 -freflection -O1 · runs live" />

The Bloomberg Clang fork with libc++ prints `WidgetImpl_size = 56` for the same source. That is the point of generating the number: each toolchain writes its own.

### The two-pass build

The public header includes the generated file and never sees `WidgetImpl`. The build runs the generator first:

```sh
g++-16 -std=c++26 -freflection generate.cpp -o build/generate
build/generate > build/widget_layout.hpp
g++-16 -std=c++26 -Ibuild widget.cpp main.cpp -o build/widget
```

The storage constructor keeps a `static_assert` as a net. When I added a `double` to `WidgetImpl` and compiled without running the generator, the build stopped:

```text
inline_pimpl.hpp:15:29: error: static assertion failed: widget_layout.hpp is stale: run the generator again
```

Running the generator again wrote 80 and the build passed. One rule matters here. `Widget` must declare its copy, move and destructor in the header and define them in the .cpp. Implicit ones would be instantiated in every user's translation unit, against an incomplete `WidgetImpl`.

## define_aggregate gives the size and gives away the members

A third way lets the compiler compute the layout in the header. The <PostLink slug="define-aggregate">define_aggregate post</PostLink> shows how a `consteval` block completes a declared class from a member list:

```cpp
struct GeneratedImpl;
consteval {
  std::meta::define_aggregate(^^GeneratedImpl, {
      std::meta::data_member_spec(^^int, {.name = "id"}),
      std::meta::data_member_spec(^^std::string, {.name = "name"}),
      std::meta::data_member_spec(^^std::string, {.name = "label"}),
  });
}
```

The size is exact, on every library, with nothing to keep in step. But the member list is in the header, and so are the includes it needs. A change to it recompiles every user, which is what a pimpl exists to prevent. The class is no longer hidden, so for a pimpl this approach is out.

## What the heap pimpl costs

The last example builds the same `Impl` five ways and counts allocations with a replaced `operator new`. The name is long enough that each string allocates once:

| design | sizeof | allocations to construct | allocations to copy |
|---|---|---|---|
| `std::unique_ptr<Impl>` | 8 | 3 | 3 |
| `std::indirect<Impl>` | 8 | 3 | 3 |
| inline buffer, size in the header | 72 | 2 | 2 |
| `Impl` as a plain member | 72 | 2 | 2 |
| `Impl` from `define_aggregate` | 72 | 2 | 2 |

The two strings account for two allocations in every row. The heap pimpls add one more, for the `Impl` itself, on every construction and every copy. The numbers are the same at `-O1` and `-O2` and on GCC trunk. The sizes are libstdc++ 16.2's.

<GodboltEmbed id="brrP5Tcd8" gccOnly gccLabel="GCC 16.2" title="Size and allocations of five pimpl designs" gcc_subtitle="x86-64 GCC 16.2 · -std=c++26 -freflection -O1 · runs live" />

So the inline buffer buys back the one allocation and costs the size of the implementation in the object. Whether that pays off depends on how many objects you make and copy. It does not change what a user recompiles.

## Which one I use

| situation | approach |
|---|---|
| the build can run a generator step | the annotated `Impl` and a generated layout header |
| one standard library, no generator | the number in the header, checked with the C++26 message |
| several standard libraries, no generator | a checked number per library, or the heap pimpl |
| the allocation does not matter | `std::indirect<Impl>`, which copies deeply with no hand-written members |
