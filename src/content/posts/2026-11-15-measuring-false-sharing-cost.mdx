## In short

- False sharing means threads write different variables that sit in one cache line. The line moves between cores, so every write waits for it.
- Eight threads, one atomic counter each, counters 8 bytes apart against padded to the interference size. The packed layout ran 13 to 88 times slower on three machines. The ratio was 13.5 on an x86-64 laptop CPU with hyperthread pairs. It was 83 on an Apple M2 Max and 88 in a Docker VM on that Mac.
- On the M2 Max, packed took 176 ns per increment and padded 2.11 ns. Padding to 64 bytes was not enough there, because the Mac reports a 128-byte cache line. On x86-64 the interference size is 64, so that gap does not appear.
- One shared counter (true sharing) cost as much as the packed layout, and padding cannot help it. A `thread_local` counter shared cache lines on macOS with GCC 16.2 but not on Linux. A stack local variable merged once matched the padded layout everywhere.
- The frequency was not controlled on any machine, the Mac was not quiet, and the x86-64 host was shared. Compare the ratios between machines, never the nanoseconds.

## What false sharing is

Cores keep their caches coherent one cache line at a time, not one variable at a time. In Ulrich Drepper's account of the MESI protocol, a write has to mark every other copy of the line as Invalid. The write is announced with a "Request For Ownership" message ([What Every Programmer Should Know About Memory](https://people.freebsd.org/~lstewart/articles/cpumemory.pdf), section 3.3.4).

False sharing follows from that. Two threads write two different variables that happen to share a line. Neither thread reads the other's variable, yet each write takes the line away from the other core. Drepper describes it in section 6.4.1: the problem shows "when all the threads are using different memory locations and are supposedly independent".

Intel's optimization manual gives the same explanation for the older Pentium 4 generation. It attributes the penalty to "cache evictions to maintain cache coherency". The source is the [IA-32 Intel Architecture Optimization Reference Manual](https://cr.yp.to/bib/2004/-intel-optimization.pdf), order number 248966-011, section "Prevent False-Sharing of Data". That edition uses 64-byte lines with a 128-byte sector, so it is an old source for the mechanism and not for today's sizes.

### How big a line is

The line size is machine specific. On the Mac used here, `sysctl hw.cachelinesize` prints 128.

The <PostLink slug="struct-layout-toolkit-reflection">struct layout toolkit post</PostLink> covers padding, the interference-size constants and cache-line budgets for reads that stream through memory. This post measures writes from several threads, which is a different cost.

## The C++ tools

The header `<new>` declares two constants. Section 17.6.6 [hardware.interference] of the [C++ draft](https://eel.is/c++draft/hardware.interference) defines them like this:

| Constant | Meaning in the draft |
|---|---|
| `hardware_destructive_interference_size` | "the minimum recommended offset between two concurrently-accessed objects to avoid additional performance degradation", where the degradation comes from contention the implementation introduces |
| `hardware_constructive_interference_size` | "the maximum recommended size of contiguous memory occupied by two objects accessed with temporal locality by concurrent threads" |

Both are at least `alignof(max_align_t)`. The draft's own example keeps two atomics apart with `alignas`:

```cpp
struct keep_apart {
  alignas(hardware_destructive_interference_size) atomic<int> cat;
  alignas(hardware_destructive_interference_size) atomic<int> dog;
};
```

I printed both constants with each compiler available here:

| Compiler and system | destructive | constructive |
|---|---|---|
| GCC 16.2.0 (Homebrew), macOS arm64 | 256 | 64 |
| Apple clang 21.0.0, macOS arm64 | 256 | 64 |
| GCC 16.2.0 (`gcc:16.2` image), Linux aarch64 in a Docker VM | 256 | 64 |
| GCC 16.2 on Compiler Explorer, x86-64 | 64 | 64 |

On the Mac the destructive value, 256, is twice the 128-byte line that `sysctl` reports. GCC's own note calls it "the default value for the current CPU tuning". Treat it as a conservative compiler default and not as a measurement.

GCC warns about the destructive constant with `-Winterference-size`. The warning appears when a header uses the constant, and its note says the value can vary with compiler version and tuning flags. With `-Werror`, the warning stops the build on both GCC systems here. A main source file compiled with `-Wall -Wextra` gave no warning, and Apple clang gave none in a header. The flag `-Wno-interference-size` silences it, and `--param=destructive-interference-size=128` changed the printed value from 256 to 128 in the Docker image.

## The experiment

T threads each increment their own counter 10,000,000 times. Only the place where the counters live changes. The layouts are:

```cpp
template <std::size_t A> struct alignas(A) AtomSlot { std::atomic<std::uint64_t> v{0}; };

std::array<AtomSlot<8>,   16> packed;       // counters 8 bytes apart
std::array<AtomSlot<std::hardware_destructive_interference_size>, 16> padded_hdis;
std::array<AtomSlot<128>, 16> padded_128;
std::array<AtomSlot<64>,  16> padded_64;
AtomSlot<std::hardware_destructive_interference_size> shared_one;  // every thread adds here
```

Two more variants need no padding. In the `thread_local` variant each thread increments its own `thread_local` object and adds it to a padded result slot at the end. In the stack local variant the counter is an ordinary local variable of the thread function, merged the same way. Each layout runs in two flavours, listed here:

| Flavour | Increment | Layouts |
|---|---|---|
| atomic | relaxed `fetch_add` on a `std::atomic<uint64_t>` | packed, three paddings, one shared counter, `thread_local`, stack local |
| plain | `++v` on a `uint64_t`, one store per iteration | the same, without the shared counter (it would be a data race) |

The increment loops are two functions that every layout calls:

```cpp
[[gnu::noinline]] void atomic_kernel(std::atomic<std::uint64_t>& v, std::uint64_t n) {
  for (std::uint64_t i = 0; i < n; ++i) v.fetch_add(1, std::memory_order_relaxed);
}
[[gnu::noinline]] void plain_kernel(std::uint64_t& v, std::uint64_t n) {
  for (std::uint64_t i = 0; i < n; ++i) { ++v; asm volatile("" : "+m"(v)); }
}
```

The `asm` statement names the counter as an in-and-out memory operand, so each iteration must store and reload it. Two things I hit while building this shaped the code. In a first version the plain loop used a different addressing mode for the packed array. It ran about six times slower than the padded one at one thread. Calling one `noinline` function through a reference gives every layout the same machine code. GCC 16.2 on macOS folded a loop over a `volatile thread_local` into a single add, which is why the barrier is an `asm` statement.

### Method

All threads wait on a spin barrier. The clock starts when the main thread releases it, and each thread records its finish time. The wall time is the last finish minus the start, divided by the increments per thread. One round runs every layout once at every thread count. A first round is discarded, and eleven more rounds are kept, so each cell has 11 runs. After each run the counters must sum to T times 10,000,000, and the program exits with an error otherwise. All 1,287 recorded runs passed.

Each table cell gives the median, then the minimum and maximum in parentheses. The last figure is the coefficient of variation: the sample standard deviation divided by the mean of the 11 runs. The unit is wall nanoseconds per increment per thread.

### Reading the atomic table

- With one thread every layout takes about 2.0 ns. The layout matters only when a second thread writes.
- The packed layout costs 9.01, 42 and 176 ns at two, four and eight threads. The second table gives 4.4, 20.4 and 83.3 times the padded value.
- Padding to 64 bytes sits between the two. At four and eight threads it took 3.80 and 5.01 ns. Padding to 128 and to 256 bytes gave the same medians, within 1%. That fits the 128-byte line that `sysctl` reports: two 64-byte slots share one line. I did not test the claim any other way.
- One shared counter costs about as much as the packed layout, for example 174 against 176 ns at eight threads. Every thread writes the same variable, so padding changes nothing.
- The stack local variable matched the padded layouts up to eight threads.

At eight threads the fastest cells are padded to HDIS (2.11 ns), padded to 128 (2.10 ns) and stack local (2.11 ns). They differ by under 1%, while the coefficients of variation are 5%, 3% and 40%. I cannot rank them. The same holds at twelve threads. Stack local took 2.96 ns, padded to 128 took 3.00 and padded to HDIS took 3.17. Coefficients of variation run from 13% to 33%.

The twelve-thread column uses the four efficiency cores too, and its spreads are wide. One packed run took 49 ns against a median of 462 ns. I do not know why.

### How quiet the host was

The host was shared. Its load average was 18.7 at the start and between 10 and 20 in bursts. A guard waited 1180 s until the 1-minute load average fell below 1.0, and it passed at 0.97. A repetition counts as noisy when the load average at its end exceeds the benchmark's own thread count by more than 1. None of the 11 repetitions of `first4` or `all` was noisy, so the tables use the raw files, which equal the filtered ones.

A third config, `percore4`, put four threads on four different cores. It produced no usable data. The load average was still decaying from the 8-thread config, so all 25 repetitions were flagged noisy. The post does not use it.

### Reading the x86-64 tables

- With one thread every layout takes about 4 ns. The layout matters only when a second thread writes.
- Packed is 5.4 to 6.2 times padded at two threads, and 13.7 to 15.0 times at four. The two four-thread ratios differ because the padded cell moved: 4.27 ns in `first4`, 5.20 ns in `all`.
- Padded to 64, padded to 128 and padded to HDIS agree within the spread. The pairing penalty that the Mac showed at 64 bytes does not occur, because the line here is 64 bytes.
- One shared counter again costs about what the packed layout costs.
- `thread_local` and stack local match the padded layout at one to four threads, as they do on Linux aarch64.

### Hyperthreads at eight threads

At eight threads the padded cells rise to 10 to 13 ns, against 4.3 to 5.2 ns at four threads. This holds for every layout, `thread_local` and stack local included, and no layout shares a cache line there. Two threads on one core share its execution resources, so I read this as SMT and not as false sharing. The 8-thread ratio of 13.5 is therefore not like-for-like with the M2 Max's eight performance cores. I did not test the SMT explanation further.

Packed over padded to HDIS is 1.4 to 1.5 at two and four threads, and 2.7 at eight threads with hyperthreads. On the ARM systems the ratio was 3.7 to 4.4 on the Mac and 4.1 to 15.9 in the Docker VM.

The file `bench-x86.s` shows the plain loop. Each iteration runs one `addq $1, (%rdi)`, a read-modify-write of memory with no `lock` prefix. Every layout calls that same function, so the padded layout does not keep its counter in a register either. The assembly does not show why the packed penalty is smaller than on ARM, and I did not test it.

## Three machines side by side

Packed over padded to HDIS for the atomic flavour, from the medians in each table:

| Machine | 1 thr | 2 thr | 4 thr | 8 thr |
|---|---|---|---|---|
| Apple M2 Max, native | 0.99 | 4.40 | 20.38 | 83.31 |
| Linux aarch64 Docker VM on the same Mac | 1.01 | 4.48 | 21.02 | 87.52 |
| x86-64 i7-10510U, CPUs 0-3 (`first4`) | 1.05 | 5.35 | 15.04 | not run |
| x86-64 i7-10510U, CPUs 0-7 (`all`) | 1.12 | 6.18 | 13.65 | 13.49 |

On all three machines a second writer in the line costs several times the padded baseline, and the cost grows with the thread count. The x86-64 ratio grows more slowly. At eight threads its 13.5 comes from hyperthread pairs, and its padded baseline is itself raised by SMT. Absolute nanoseconds are not comparable across these machines, because none had a fixed clock.

## thread_local counters shared lines on macOS

On the Mac, the atomic `thread_local` row follows the packed layout: 9.51 ns at two threads, 44 at four and 118 at eight. Its spreads are wide (1.99 to 12 ns at two threads). The same variant on Linux costs the same as the padded layout.

A small program, `tls_addresses.cpp`, starts eight threads, keeps them alive, and compares the addresses of their `thread_local` counters. On macOS the smallest gap between two threads' counters was 16 bytes, with both GCC 16.2 and Apple clang 21. In the committed run, 3 of the 28 thread pairs fell in one 128-byte block with GCC and 4 with Apple clang. Other runs of the same program gave other counts (6 with GCC and 2 with Apple clang in an earlier run). In the Docker image the smallest gap was 8,454,144 bytes.

GCC on macOS compiled the access to a call of the emulated-TLS function in its generated code. I did not look at what Apple clang generates, and I did not time Apple clang. The timing result above is for GCC. The conclusion that I can support is narrow. A `thread_local` variable is not automatically a private cache line on macOS, so a tiny per-thread counter can false-share there.

A stack local variable merged once at the end avoided the problem on all three machines. The merge target in this program is a padded slot, written once per thread.

### On x86-64 Linux

The `thread_local` row matches the padded layout, as in the Docker VM. In `first4` it took 4.22 against 4.16 ns at two threads, and 4.66 against 4.27 ns at four. I did not run `tls_addresses.cpp` there.

## A layout and correctness check on Compiler Explorer

Compiler Explorer is a shared machine, so it runs no timings here. The demo checks layout and correctness only:

```cpp
static_assert(sizeof(Packed) == 16 && offsetof(Packed, b) == 8);
static_assert(alignof(Padded) == kDestructive && offsetof(Padded, b) == kDestructive);
static_assert(alignof(Fixed128) == 128 && offsetof(Fixed128, b) == 128);
```

It then runs two threads on each struct and checks that both counters add up. It prints the constants and the sizes, exits with 0, and shows `destructive=64` on Compiler Explorer's x86-64 GCC 16.2.

## What this has not been tested on

- Other x86-64 CPUs. One laptop part was measured, on a shared host, with turbo on and the governor on `powersave`. Server parts and AMD cores may differ.
- Other Arm chips, including other Apple generations and server cores with different line sizes.
- A pinned macOS run. The system has no affinity API, so I cannot say which core type a thread used.
- Hyperthreading as a cause. The M2 Max has no SMT. The x86-64 8-thread cells use hyperthread pairs, and the `percore4` run that would separate cores from siblings produced no usable data.
- Clang against GCC on Linux. Apple clang was used only for the constants and the address check, not for timings.
- Core counts above 12, and a quiet Mac. The load listed above was not zero.
- Real workloads. The program does nothing but increment a counter.
- Frequency control. None of the three machines fixed the clock.
